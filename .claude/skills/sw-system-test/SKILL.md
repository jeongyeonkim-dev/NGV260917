# SW 시스템 테스트 케이스 생성 (A-SPICE SWE.6 · ISO 26262 Part 6 정합)

## 개요

SW 요구사항 명세서를 근거로, **통합이 완료된 소프트웨어 전체**가 요구사항을 만족하는지 검증하는 시스템 테스트 케이스를 설계하는 방법론 스킬이다(A-SPICE 4.1 **SWE.6 소프트웨어 검증**, `references/aspice-swe6-bp.md` 참조). "무엇을 근거로, 어떤 기법으로, 어떤 원칙으로" 테스트 케이스를 설계할지의 방법론만 정의한다. 요구사항 분석, 사용자와의 확인, 실제 산출물(xlsx) 작성은 이 스킬을 사용하는 에이전트(`sw-system-tester`)가 수행한다.

## 이 스킬의 경계 (다루지 않는 것)

이 프로젝트는 소프트웨어 테스트를 3단계로 나눈다 — 아래 표에서 **이 스킬이 담당하는 것은 SWE.6뿐**이다. 다른 두 단계는 각각 별도 스킬이 이미 담당하므로 중복 정의하지 않는다.

| 단계 | A-SPICE | 테스트 베이시스 | 담당 스킬 |
|------|---------|------------------|-----------|
| 단위 테스트 | SWE.4 | 상세설계의 단위 인터페이스 | `tdd` (구현 단계, `coding` 서브에이전트가 사용) |
| 컴포넌트 통합시험 | SWE.5 | 아키텍처의 컴포넌트 인터페이스 명세 + 통합 순서 | `integration-testing` (`integration-tester` 서브에이전트가 사용) |
| **시스템(소프트웨어) 검증** | **SWE.6** | **SW 요구사항 명세서** | **이 스킬** |

- 컴포넌트 간 인터페이스 자체의 정합성, 통합 순서·사전조건 준수, 함수/Call 커버리지는 `integration-testing` 스킬의 소관이다 — 이 스킬에서 다시 다루지 않는다.
- 코드 단위의 화이트박스 테스트(경계값을 코드 분기까지 추적하는 것)는 `tdd` 스킬의 소관이다. 이 스킬은 블랙박스(요구사항 기반) 관점만 다룬다.
- 세 스킬 모두 같은 핵심 설계 기법(경계값분석/동등분할/오류추측)을 공유하지만, 그 **정의는 `tdd` 스킬의 `test-case-design.md`를 원본으로 삼아 재사용**한다 — 이 스킬은 시스템/블랙박스 테스트에서만 필요한 것(조합/페어와이즈, ISO 29119 용어, ISO 25010 품질특성별 NFR 분류)만 추가로 정의한다(아래 "적용 대상 테스트 기법" 참조).

## 기반지식

- **A-SPICE SWE.6 (소프트웨어 검증)**: "통합된 소프트웨어가 소프트웨어 요구사항과 일관됨을 검증한다"는 목적, 검증측정 명세·선정·수행, 요구사항↔검증측정↔검증결과 양방향 추적을 요구한다. 전체 베이스프랙티스는 `references/aspice-swe6-bp.md` 참조.
- **ISO 26262 Part 6 (소프트웨어 안전요구사항 검증 관련 절)**: 검증기법 선정은 요구사항의 성격에 좌우된다 — 데이터 범위 지향 요구사항에는 경계값·동등분할, 정상/오류 구분에는 긍정(sunny-day)/부정(결함주입 등) 시험, 그 외에는 지식·경험 기반 오류추측(A-SPICE SWE.6.BP1 Note 1이 그대로 이 근거를 명시한다). 정확한 절·표 번호는 판(2011/2018)마다 다르므로 인증심사용으로는 조직 보유 정본과 대조한다.
- **ISO 29119 / ISTQB**: 테스트 시나리오·테스트 케이스 설계 프로세스와 용어 체계(긍정/부정 분류 등)의 근거.
- **ISO/IEC 25010:2023 (SQuaRE 제품 품질 모델)**: 비기능 요구사항 분류 기준. **이 프로젝트는 `requirements-analyst` 스킬이 이미 채택한 9개 품질특성 체계(2023년판, 안전성 신설·상호작용역량/유연성으로 개편됨)를 그대로 쓴다** — 별도의 구버전 8특성 체계(사용성/이식성 등 옛 명칭)를 쓰지 않는다. 목록과 하위특성 정의는 `requirements-analyst` 스킬의 `references/iso25010-nfr-checklist.md`를 그대로 참조한다.

## 적용 대상 테스트 기법

**공통 기법(정의는 `tdd` 스킬의 `references/test-case-design.md`를 그대로 따름, 여기서 재정의하지 않음)**: 경계값 분석, 동등분할, 오류추측(경험 기반 테스트 포함).

**이 스킬에서만 추가로 정의하는 기법(시스템/블랙박스 테스트 고유)**:
- **조합 테스트(전 조건 조합)**: 관련 조건 수가 적어 전수 조합이 실행 가능한 범위일 때 우선 적용한다.
- **페어와이즈**: 조건·값의 조합 수가 많아 전수 조합이 비현실적일 때 대체 적용한다.

각 테스트 케이스의 "사용 기법" 항목에 실제로 적용한 기법을 명시한다(공통 기법이든 이 스킬 고유 기법이든 동일하게 기록).

## 긍정/부정 케이스 분류 (필수, 프로젝트 전체 공통 규칙)
A-SPICE SWE.6.BP1 Note 1이 명시하듯 검증측정은 "긍정(sunny-day) 시험 대 부정 시험(결함주입 등)"을 구분한다. `tdd`/`integration-testing` 스킬과 동일하게, 이 스킬로 만드는 모든 시스템 테스트 케이스도 **긍정(Positive)/부정(Negative)** 을 명시적으로 표기한다(작성 에이전트의 필수 필드, 아래 "산출물 구조" 참조). 하나의 요구사항에 긍정 케이스만 있고 부정 케이스가 없다면(또는 그 반대) 미완성으로 간주한다.

## 비기능 테스트 케이스 분류
비기능 테스트 케이스는 `requirements-analyst`의 ISO/IEC 25010:2023 9개 품질특성(성능효율성/호환성/상호작용역량/신뢰성/보안성/유지보수성/유연성/안전성, 기능적합성은 FR 영역이므로 제외)별로 그룹화한다. 요구사항 명세서에 이미 특성 태그(예: `SW-REQ-0034-PERF`)가 붙어 있으면(`requirements-analyst`의 `traceability-scheme.md` 채번 규칙) 그 태그를 그대로 이어받아 분류한다 — 임의로 다른 분류 체계를 만들지 않는다.

## 추적성 (기존 스킴 재사용, 새로 만들지 않음)
`requirements-analyst` 스킬의 `references/traceability-scheme.md`에 정의된 ID 체계(SW-REQ-####)를 "대상 요구사항" 컬럼에 그대로 쓴다. 시스템 테스트 케이스 자신의 ID는 `TC-SYS-####` 접두사를 사용하고, 가능하면 `requirements-analyst`/`architecture-designer`/`detailed-design`/`integration-testing`이 공유하는 것과 같은 추적매트릭스에 행을 추가한다(별도 매트릭스를 새로 만들지 않는다).

## 시험 성공률 목표 (CLAUDE.md 근거, 필수)
CLAUDE.md 시스템 테스트 지침에 따라 **시스템 테스트 성공률은 100%여야 한다** — 작성된 모든 테스트 케이스가 최종적으로 통과(Pass) 상태여야 릴리스 가능하다고 본다.
- 실패한 케이스가 있으면 결함으로 SUP.9(문제해결관리) 절차로 넘기고, 수정 후 재검증해 통과시킨다.
- 요구사항이 모호해서 실패인지 결함인지 판단하기 어려우면, 임의로 "예상과 다르니 통과로 간주"하지 않는다 — 사용자에게 확인한다.
- 100%를 채우기 위해 실패하는 케이스를 삭제하거나 판정기준을 사후에 완화하지 않는다(성공률을 조작하지 않는다). 판정기준 자체를 바꿔야 한다면 "확정 근거" 열에 사유·승인자를 남기고 정식으로 갱신한다.

## 작성 원칙

- 의미 없이 테스트 커버리지 수치 달성만을 목적으로 하는 케이스는 생성하지 않는다 — 이 원칙의 상세 근거(테스트는 자신이 잡아내는 결함의 이름을 댈 수 있어야 한다)는 `tdd` 스킬의 `references/writing-good-tests.md` "원칙 1: 깨짐에 이름 붙이기"를 참조한다(코드 mock 관련 내용은 이 스킬에는 해당하지 않으므로 그 부분은 적용 제외).
- 테스트의 예상 결과를 임의로 가정하지 않는다. 명세서에 근거가 없다면 이 스킬을 사용하는 에이전트가 사용자에게 확인을 받는다.
- 프로젝트에서 정한 테스트 커버리지 목표(예: CLAUDE.md에 명시된 기준)를 준수한다. 단, 함수/Call 커버리지 같은 구조적(화이트박스) 지표는 이 스킬의 책임이 아니다 — `integration-testing` 스킬의 소관이다.
- 실행자가 그대로 재현할 수 있는, 실행 가능한 테스트 케이스만 작성한다.
- 기법 선택이나 커버리지 범위 설정이 판단하기 어려운 경우 임의로 결정하지 말고, 이 스킬을 사용하는 에이전트를 통해 사용자 검토를 받는다.
- 명세서에 직접적 근거는 없으나 QA 관점에서 추가를 제안하고 싶은 테스트 케이스는 테스트 케이스명 끝에 "(제안)"이라고 표시해 구분한다.

## 도구 사용

- 페어와이즈 조합을 생성할 때는 오픈소스인 PICT를 사용한다.
- 전수 조합(모든 조건의 조합)을 생성할 때는 PICT의 `/o:max` 옵션을 사용한다.

## 산출물 구조

- 기능 요구사항에 대한 테스트 케이스: "테스트 케이스" 시트. 최소 컬럼 — 테스트 케이스 ID(`TC-SYS-####`), 대상 요구사항(`SW-REQ-####`), 테스트 목적/설명, 사전조건, 테스트 절차, 입력값, 예상 결과, **긍정/부정**, 우선순위, 사용 기법.
- 비기능 요구사항에 대한 테스트 케이스: 별도의 "비기능 테스트 케이스" 시트, ISO/IEC 25010:2023 품질특성별로 구분(위 "비기능 테스트 케이스 분류" 참조). 같은 필수 컬럼(긍정/부정 포함)을 유지한다.
- 요구사항 원문에 없거나 원문보다 엄격하게, 사용자 확인을 거쳐 확정한 판정기준: "확정 근거" 열에 확정 일자와 승인 주체를 기록한다.
