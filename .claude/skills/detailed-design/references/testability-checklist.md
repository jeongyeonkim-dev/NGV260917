# 테스트 용이성 체크리스트 (SWE.4 단위검증 대비)

상세설계 단계에서 테스트 용이성을 확보해두면, 다음 단계인 SWE.4(소프트웨어 단위 검증)에서의 재작업을 줄일 수 있다. 아래 항목을 상세설계 검토 시 함께 확인한다.

## 관측 가능성 (Observability)
- 단위의 출력값과, 필요한 경우 내부 상태를 외부(테스트 하네스)에서 확인할 수 있는 인터페이스가 있는가?
- 실패/예외 상황이 조용히 삼켜지지 않고 관측 가능한 형태(반환코드, 상태 플래그, 로그)로 노출되는가?

## 제어 가능성 (Controllability)
- 단위를 외부에서 독립적으로 호출·자극할 수 있는가(다른 단위의 복잡한 초기화 없이 호출 가능한가)?
- 경계값·예외 입력(유효범위의 최소/최대/범위 밖 값)을 테스트가 직접 주입할 수 있는 구조인가?

## 의존성 격리 (Dependency Isolation)
- 단위가 다른 컴포넌트/단위에 의존할 때, 그 의존 대상이 인터페이스(추상화)를 통해 주입되는가(architecture-designer의 DIP 원칙)? 그렇다면 테스트 시 스텁/모의객체로 대체 가능하다.
- 하드웨어 접근, 전역 상태, 시간(현재 시각) 등 테스트를 어렵게 만드는 요소가 인터페이스 뒤로 격리되어 있는가?

## 복잡도 (Complexity)
- 순환복잡도가 과도하게 높지 않은가(`iso26262-6-unit-design-principles.md`의 낮은 복잡도 원칙)? 복잡도가 높으면 필요한 테스트 케이스 수가 기하급수적으로 증가한다.
- 하나의 단위가 여러 책임을 섞고 있어 테스트 시나리오가 서로 얽히지 않는가?

## 결정성 (Determinism)
- 동일 입력에 대해 항상 동일 출력을 내는가(비결정적 동작 — 예: 초기화되지 않은 메모리, 경쟁 조건 — 이 없는가)? 비결정적 동작은 테스트 결과의 재현성을 해친다.

## 이 체크리스트의 결과 활용
상세설계 산출물의 "테스트 용이성 점검 결과" 절에 항목별 확인 여부와, 미흡한 경우의 보완 계획을 기록한다. 이 기록은 SWE.4 스킬/에이전트가 단위 테스트 케이스를 설계할 때 직접적인 입력이 된다.
