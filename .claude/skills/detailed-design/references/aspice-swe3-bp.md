# A-SPICE 4.1 SWE.3 베이스프랙티스 근거

> 출처: VDA QMC, *Automotive SPICE® PAM*, Version 4.1(예비판, 2026-04-16), §4.4.3(SWE.3). 영문 원문을 한국어로 옮기고 체크포인트를 덧붙였다.

## SWE.3 — 소프트웨어 상세설계 및 단위 구현 (Software Detailed Design and Unit Construction)

**목적**: 소프트웨어 아키텍처와 일관된, 정적·동적 측면을 포함한 소프트웨어 상세설계를 수립하고, 상세설계와 일관되게 소프트웨어 단위를 구현한다.

**성과항목(Outcome)**
1. 정적·동적 측면을 포함한 상세설계가 명세된다.
2. 상세설계에 명시된 대로 소프트웨어 단위가 구현된다.
3. 상세설계와 소프트웨어 아키텍처 간 일관성과 양방향 추적성이 수립된다.
4. 소스코드와 상세설계 간 일관성과 양방향 추적성이 수립된다.
5. 상세설계와 소프트웨어 요구사항 간 일관성과 양방향 추적성이 수립된다.
6. 소스코드와 합의된 상세설계가 모든 이해관계자에게 전달된다.

**베이스프랙티스**
- **BP1 — 정적 측면 명세**: 각 소프트웨어 컴포넌트에 대해, 그 소프트웨어 단위들의 행위, 정적 구조·관계, 인터페이스를 명세한다. 인터페이스에는 **입출력에 대한 유효 데이터 값 범위**(응용영역 관점)와 **입출력에 적용되는 물리/측정 단위**(응용영역 관점)를 포함한다.
  - 참고: 소프트웨어 단위의 경계는 소스코드 내 표현(서브루틴 1개 또는 여러 개)과 독립적이며, 응용영역의 의미에 따라 결정된다.
  - 참고: 유효 데이터 값 범위와 물리단위의 예 — `0..200 [m/s]`, `0..3.8 [A]`, `1..100 [N]`. 이런 응용영역 값 범위를 프로그래밍 언어 수준 데이터 타입(예: 0..65535 범위의 unsigned Integer)으로 매핑하는 것은 BP2의 영역이다.
  - 참고: 카운터처럼 물리단위도 측정단위도 적용되지 않는 파라미터/반환값도 있을 수 있다.
  - 참고: 하드웨어-소프트웨어 인터페이스(HSI) 정의는 시스템 설계(SYS.3)의 영역이다.
- **BP2 — 동적 측면 명세**: 소프트웨어 아키텍처를 기준으로, 컴포넌트의 동적 행위를 구현하기 위한 관련 소프트웨어 단위 간 상호작용을 포함한 동적 측면을 명세·문서화한다. (행위 서술 예: 자연어 또는 SysML/UML 같은 반정형 표기)
- **BP3 — 소프트웨어 단위 개발**: 상세설계와 일관되게, 그리고 **코딩 원칙**에 따라 소프트웨어 단위를 개발·문서화한다.
  - 참고: CL1 수준의 코딩 원칙 예 — 암묵적 타입변환 미사용, 서브루틴의 단일 진입점·단일 탈출점, 범위검사(설계에 의한 계약, 방어적 프로그래밍). 추가 예시는 ISO 26262-6 Clause 8.4.5와 Table 6을 참고한다.
- **BP4 — 일관성 확보 및 양방향 추적성 수립**: 아래 세 가지를 모두 확보한다 — (a) 상세설계 ↔ 소프트웨어 아키텍처, (b) 개발된 소프트웨어 단위 ↔ 상세설계, (c) 상세설계 ↔ 소프트웨어 요구사항.
  - 참고: 중복된 추적 경로를 만들지 않도록 접근방식을 조합해 사용한다.
  - 참고: 상세설계 내 소프트웨어 단위를 소프트웨어 요구사항에 직접 추적하는 예로 커뮤니케이션 매트릭스, 또는 AUTOSAR 설정에 내재된 진단 식별자 목록 같은 베이스소프트웨어 측면이 있다.
  - 참고: 추적 링크의 존재 자체가 정보의 일관성을 의미하지는 않는다.
- **BP5 — 합의된 상세설계와 단위 전달**: 합의된 상세설계와 개발된 소프트웨어 단위를 모든 이해관계자에게 전달한다.

**출력 산출물**: 04-05 소프트웨어 상세설계(Software Detailed Design), 11-05 소프트웨어 단위(Software Unit), 13-51 일관성 증적, 13-52 커뮤니케이션 증적
