# ISO 26262-6 Clause 8 소프트웨어 단위 설계·구현 원칙 (요약·재구성)

> 근거: ISO 26262-6:2018, Clause 8 "Software unit design and implementation"(소프트웨어 단위 설계 및 구현), 특히 단위 설계원칙 표. **아래 내용은 표준 원문의 verbatim 인용이 아니라 업계에 널리 공유된 요지를 한국어로 재구성한 것**이다 — 인증심사·법적 근거가 필요하면 반드시 조직이 보유한 정본 Clause 8과 조항번호를 대조 확인한다. A-SPICE PAM 4.1 SWE.3.BP3 Note 7도 "추가 예시는 ISO 26262-6 Clause 8.4.5와 Table 6을 참고하라"고 직접 언급한다(`aspice-swe3-bp.md` 참조).

## 단위 설계원칙

| 원칙 | 요지 | 이유 |
|------|------|------|
| 단일 진입점·단일 탈출점 | 서브루틴/함수는 하나의 진입점과 하나의 탈출점만 가진다 | 제어흐름을 예측 가능하게 하고 리뷰·테스트를 단순화 |
| 구조적 제어흐름 | 무조건 분기(goto 등 비구조적 점프)를 피한다 | 제어흐름 추적성과 정적분석 신뢰도 향상 |
| 재귀 사용 제한 | 재귀를 피하거나 제한적으로만 사용한다 | 스택 사용량과 종료 조건 예측이 어려워짐 |
| 포인터 사용 제한 | 포인터 연산을 제한하고, 사용 시 안전한 패턴을 따른다 | 포인터 오용은 메모리 결함과 결합도 증가의 주요 원인 |
| 동적 객체/변수 사용 제한 | 초기화 이후 런타임 동적 할당을 피하거나, 사용 시 온라인 테스트를 병행한다 | 메모리 단편화·할당 실패의 예측 불가능성 방지 |
| 암묵적 타입변환 금지 | 명시적 캐스팅만 허용한다 | 값 손실·오버플로우 등 은닉된 결함 방지 |
| 은닉된 데이터/제어흐름 금지 | 매크로, 부작용(side effect)이 있는 표현식 등으로 흐름을 숨기지 않는다 | 코드를 읽는 것만으로 동작을 예측할 수 있어야 함 |
| 낮은 복잡도 유지 | 순환복잡도(cyclomatic complexity) 등 정량 지표로 복잡도를 제한한다 | 복잡도가 높을수록 결함 밀도와 테스트 難이도가 증가 |
| 안전한 언어 서브셋 사용 | 언어의 위험한 기능을 제한하는 코딩 가이드라인(예: C의 MISRA C, C++의 MISRA C++/AUTOSAR C++14)을 따른다 | 알려진 위험 패턴을 사전에 차단 |
| 범위검사·방어적 프로그래밍 | 입력값을 설계된 유효범위 내에서만 처리하도록 검사한다(design-by-contract) | SWE.3.BP1에서 정의한 유효 데이터 값 범위를 실제 코드에서 강제 |

## 단위 설계 표기법
자연어(비정형), 흐름도·의사코드·상태다이어그램(반정형), 수학적 표현(정형) 중 ASIL과 복잡도에 맞는 표기를 선택한다. `references/unit-notation.md`에서 실무 표기 가이드를 다룬다.

## 이 스킬에서의 적용
- SKILL.md 4단계에서 위 원칙을 상세설계 문서에 명시적으로 반영하고, 각 단위가 원칙을 어떻게 지키는지(또는 예외 사유·완화조치) 기록한다.
- 예외가 필요한 경우(예: 성능상 불가피한 재귀), 사유와 대안 검증방법(예: 스택 사용량 정적분석)을 함께 기록한다 — 예외를 그냥 무시하지 않는다.
- SWE.3.BP1이 요구하는 "입출력 유효 데이터 값 범위·물리단위 명시"는 이 표의 "범위검사·방어적 프로그래밍" 원칙을 코드 수준에서 실행하기 위한 전제조건이다 — 범위가 명시되지 않으면 방어적 검사 자체를 설계할 수 없다.
