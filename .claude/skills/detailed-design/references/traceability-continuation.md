# 3단 양방향 추적성 — 상세설계 확장

> `requirements-analyst` 스킬의 `traceability-scheme.md`(요구사항 ID 체계)와 `architecture-designer` 스킬의 추적 원칙을 그대로 계승하고, 소프트웨어 단위 수준으로 확장한다.

## ID 채번 규칙 확장

| 레벨 | 접두사 | 예시 | 대응 A-SPICE 산출물 |
|------|--------|------|------------------------|
| (기존) 소프트웨어 요구사항 | `SW-REQ-####` | SW-REQ-0034 | SWE.1 |
| (기존) 아키텍처 컴포넌트 | `architecture-designer`가 정한 컴포넌트 ID | Comp-A | SWE.2 |
| **소프트웨어 단위** | `UNIT-<컴포넌트ID>-####` | UNIT-CompA-001 | SWE.3 (11-05 Software Unit) |
| **소스코드** | 파일 경로 + 함수/모듈명 (버전관리 커밋 해시로 시점 고정) | `src/comp_a/foo.c :: calc_speed()` | SWE.3 (코드) |

## SWE.3.BP4가 요구하는 세 방향 추적

상세설계 문서와 추적매트릭스에는 아래 세 가지가 모두 채워져야 한다(하나라도 비면 미완성으로 표시):

1. **상세설계 ↔ 소프트웨어 아키텍처**: 각 단위가 어느 컴포넌트에 속하는지, 그 컴포넌트의 어느 책임을 구현하는지.
2. **상세설계 ↔ 소프트웨어 요구사항**: 각 단위(또는 단위 그룹)가 어느 SW-REQ-####를 충족하는지. 커뮤니케이션 매트릭스나 진단 식별자 목록 같은 기존 산출물을 재사용해도 된다(중복 경로 생성 지양, SWE.3 Note 8).
3. **소스코드 ↔ 상세설계**: 실제 구현된 코드 위치가 어느 단위 설계를 구현한 것인지. 코드가 아직 없으면 "미구현"으로 명시한다.

## 추적매트릭스 통합
`requirements-analyst`·`architecture-designer`가 사용하는 것과 동일한 추적매트릭스(권장 경로: `docs/traceability/trace-matrix.md`)에 소프트웨어 단위 행을 추가한다. 별도 매트릭스를 새로 만들지 않는다 — 하나의 매트릭스에서 요구사항→아키텍처→상세설계→코드 전 구간을 조회할 수 있어야 한다.

```
| ID | 유형 | 상위 추적 | 하위 추적 | 커버리지 상태 |
|----|------|-----------|-----------|----------------|
| SW-REQ-0034 | 소프트웨어 요구사항 | SYS-REQ-0012 | Comp-A, UNIT-CompA-001 | OK |
| Comp-A | 아키텍처 컴포넌트 | SW-REQ-0034 | UNIT-CompA-001, UNIT-CompA-002 | OK |
| UNIT-CompA-001 | 소프트웨어 단위 | Comp-A, SW-REQ-0034 | src/comp_a/foo.c::calc_speed() | OK |
| UNIT-CompA-002 | 소프트웨어 단위 | Comp-A | 미구현 | 갭(코드 없음) |
```

## 이상 패턴 점검 (기존 스킴에 추가)
- **레벨 건너뛰기**: 단위가 요구사항에는 연결되어 있는데 소속 컴포넌트가 명시되지 않은 경우(또는 그 반대) — 세 방향 중 하나가 비어 있다는 뜻이므로 즉시 보정한다.
- **범위 불일치**: 단위의 유효 데이터 값 범위(`unit-interface-and-datarange.md`)가 상위 요구사항의 정량 기준(`requirements-analyst`의 수용기준)과 모순되는 경우 — 일관성 위반으로 기록한다.
- **코드 없는 장기 미구현 단위**: 상세설계 완료 후 상당 기간 코드가 연결되지 않는 단위는 프로젝트 진행상황 보고에 별도로 표기한다.
