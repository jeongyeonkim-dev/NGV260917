# 상세설계 스킬 (A-SPICE SWE.3 · ISO 26262 Part 6 Clause 8 정합)

지정된 설계서 양식에 맞춰, A-SPICE 4.1 SWE.3(소프트웨어 상세설계 및 단위 구현)과 ISO 26262 Part 6 Clause 8(소프트웨어 단위 설계·구현)을 만족하는 상세설계를 작성한다. 상세설계는 `architecture-designer` 스킬이 만든 소프트웨어 아키텍처(컴포넌트, 인터페이스)를 입력으로 받아, 각 컴포넌트를 **소프트웨어 단위(unit)** 수준까지 구체화하는 단계다. 이 스킬의 목표는 다음 품질 게이트를 모두 통과하는 상세설계를 만드는 것이다.

1. **설계서 양식 준수**
2. **표준 준수** — A-SPICE SWE.3 베이스프랙티스, ISO 26262-6 Clause 8 단위 설계원칙
3. **상위 아키텍처 원칙 계승(필수)** — `architecture-designer`에서 정한 응집도/결합도/SOLID/인터페이스 전용 통신 원칙이 단위 수준에서도 깨지지 않아야 한다.
4. **입출력 데이터의 유효범위·물리단위 명시(필수)** — 모든 단위 인터페이스의 파라미터에 값 범위와 단위(unit)를 명시한다.
5. **안전 코딩 원칙 준수** — one entry/one exit, 제어흐름 단순화, 포인터·재귀·동적메모리 제한 등.
6. **테스트 용이성 고려** — 다음 단계(SWE.4 단위검증)를 염두에 둔 관측 가능성·제어 가능성 확보.
7. **3단 양방향 추적성** — 요구사항 ↔ 아키텍처 ↔ 상세설계 ↔ 코드.

근거 표준 원문과 체크리스트는 `references/`에 있다.

## 0단계 — 설계서 양식 확인 (선행 조건)

`references/template.md`를 먼저 읽는다. **"임시(INTERIM)"** 표시가 있으면 사용자가 실제 상세설계서 양식을 아직 제공하지 않은 것이다 — 임시 양식으로 초안 작성은 가능하되, 산출물 상단에 "⚠ 사용자 지정 설계서 양식 미수령 — 임시 양식 기준" 경고를 표기한다. 실제 양식을 받으면 이 파일을 교체한다.

## 절차

### 1단계 — 입력 확인
- `architecture-designer` 스킬이 만든 소프트웨어 아키텍처 산출물(컴포넌트 목록, 컴포넌트 책임, 인터페이스 명세)을 확인한다. 없으면 사용자에게 아키텍처 산출물의 위치를 먼저 확인한다 — 아키텍처 없이 상세설계로 바로 들어가지 않는다.
- 상세설계 대상 컴포넌트 범위를 확정하고, 관련 소프트웨어 요구사항(SW-REQ-####, `requirements-analyst` 스킬 ID 체계)을 확인한다.

### 2단계 — 정적 측면 상세설계 (필수: 데이터 유효범위·단위 명시)
각 소프트웨어 컴포넌트를 소프트웨어 단위(subroutine/함수/클래스 등, 언어·구현 방식에 독립적으로 정의)로 분해한다(SWE.3.BP1). 각 단위에 대해:
- 행위, 정적 구조·관계, 인터페이스(입력/출력)를 정의한다.
- **모든 입출력 파라미터에 유효 데이터 값 범위(예: `0..200 [m/s]`)와 물리/측정 단위(있는 경우)를 명시한다.** 물리 단위가 없는 파라미터(카운터 등)는 "단위 없음"으로 명시한다.
- `architecture-designer` 스킬의 `interface-first-design.md` 규칙(방향, 타이밍, 오류처리 등)을 단위 수준까지 그대로 적용한다 — 단위 간 통신도 정의된 인터페이스로만 이루어져야 한다(전역변수·직접 필드 접근 금지는 단위 레벨에서도 유효하다).
- `references/unit-interface-and-datarange.md` 체크리스트로 완결성을 확인한다.

### 3단계 — 동적 측면 상세설계
관련 단위들이 컴포넌트의 동적 행위를 구현하기 위해 어떻게 상호작용하는지(호출 순서, 상태 전이, 타이밍)를 정의한다(SWE.3.BP2). `references/unit-notation.md`의 표기법(의사코드, 흐름도, 상태다이어그램, 시퀀스 다이어그램)을 사용한다.

### 4단계 — 안전 코딩 원칙 적용
`references/iso26262-6-unit-design-principles.md`의 원칙(1진입/1탈출, 제어흐름 단순화, 포인터·재귀·동적메모리 제한, 암묵적 타입변환 금지, 은닉된 데이터/제어흐름 금지, 순환복잡도 상한, 언어 서브셋 사용)을 상세설계 문서에 명시적으로 반영한다. 각 단위 설계가 이 원칙을 어떻게 지키는지(또는 예외 사유) 기록한다.

### 5단계 — 상위 아키텍처 원칙 계승 재검토 (필수)
`architecture-designer` 스킬에서 정한 원칙이 단위 분해로 인해 훼손되지 않았는지 재확인한다:
- 하나의 단위가 여러 컴포넌트의 책임을 대신 흡수하고 있지 않은가(응집도 위반)?
- 단위 분해 결과 컴포넌트 간 결합도가 오히려 높아지지 않았는가(예: 한 컴포넌트의 단위가 다른 컴포넌트 내부 단위를 직접 호출)?
- SOLID 원칙(특히 SRP, DIP)이 단위 수준에서도 유지되는가?
위반이 발견되면 단위 분해를 재조정한다.

### 6단계 — 이해가능성 검토
`requirements-analyst` 스킬의 `references/iso26262-requirements-criteria.md` 체크리스트(비모호성, 이해가능성, 원자성, 일관성)를 상세설계 문서의 서술 부분에도 동일하게 적용한다. 상세설계는 구현자가 추가 질문 없이 코드를 작성할 수 있을 정도로 구체적이어야 한다.

### 7단계 — 테스트 용이성 확보 (다음 단계 SWE.4 대비)
`references/testability-checklist.md`를 참고해 각 단위가 다음을 만족하는지 확인한다: 관측 가능성(단위의 출력·상태를 외부에서 확인 가능), 제어 가능성(단위를 독립적으로 호출·자극 가능), 의존성 주입 가능 여부(단위 검증 시 의존 대상을 스텁/모의객체로 대체 가능한 구조인지 — architecture-designer의 DIP 원칙과 연결).

### 8단계 — 3단 양방향 추적성 확보
`references/traceability-continuation.md`의 규칙에 따라 소프트웨어 단위에 ID를 부여하고, 세 방향의 추적을 모두 채운다(SWE.3.BP4가 요구하는 세 가지 일관성·추적):
- 상세설계 ↔ 소프트웨어 아키텍처
- 상세설계 ↔ 소프트웨어 요구사항
- 소스코드 ↔ 상세설계
`requirements-analyst`·`architecture-designer` 스킬과 동일한 추적매트릭스에 통합해서 관리한다. 추적 링크의 존재만으로 충분하지 않다 — 연결된 산출물의 내용이 실제로 부합하는지 확인한다(SWE.3 Note 10).

### 9단계 — 산출물 작성 및 전달
0단계에서 확인한 양식에 맞춰 최종 문서를 작성한다. 양식이 없으면(임시 상태) 아래 최소 구성을 쓴다:

```
## 상세설계 개요
- 대상 컴포넌트, 관련 아키텍처 요소 ID, 관련 요구사항 ID

## 단위 목록 및 정적 구조
| 단위 ID | 소속 컴포넌트 | 책임(1문장) | 비고 |

## 단위 인터페이스 명세
| 단위 ID | 파라미터 | 방향 | 데이터 타입 | 유효범위 | 단위(unit) | 오류처리 |

## 동적 측면
- 단위 간 호출순서/상태전이 다이어그램

## 안전 코딩 원칙 반영 현황
| 원칙 | 반영 방법 / 예외 사유 |

## 테스트 용이성 점검 결과

## 추적성
- 요구사항 ↔ 아키텍처 ↔ 상세설계 ↔ (예정)코드 매핑 표
```

합의된 상세설계는 이해관계자에게 전달 가능한 형태로 정리한다(SWE.3.BP5).

## 주의사항
- 아키텍처 산출물 없이 상세설계를 시작하지 않는다 — 반드시 1단계에서 먼저 확인한다.
- 데이터 유효범위·물리단위 명시는 "권장"이 아니라 **필수**다. 빠진 파라미터는 미완성으로 표시하고 보완한다.
- 상위 아키텍처의 응집도/결합도/SOLID/인터페이스 전용 통신 원칙은 단위 수준에서 재해석되는 것이지, 면제되는 것이 아니다.
