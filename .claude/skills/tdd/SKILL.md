# TDD 스킬 (Red-Green-Refactor, Python unittest 기준)

> 출처: 이 스킬은 [obra/superpowers](https://github.com/obra/superpowers)의 `test-driven-development` 스킬(MIT License, Copyright (c) 2025 Jesse Vincent)을 골격으로 삼아, Python/unittest 환경과 이 프로젝트의 상세설계·품질지표 체계에 맞게 각색한 것이다. 라이선스 전문은 `references/ATTRIBUTION.md`에 있다.

## 이 스킬의 경계 (다루지 않는 것)
이 스킬은 **A-SPICE SWE.4(소프트웨어 단위 검증)** 수준 — 즉 상세설계의 단위 인터페이스를 베이시스로 한 화이트박스 단위테스트만 다룬다. 컴포넌트 인터페이스·통합 순서를 베이시스로 하는 통합시험(SWE.5)은 `integration-testing` 스킬, SW 요구사항 명세서를 베이시스로 한 블랙박스 시스템 검증(SWE.6)은 `sw-system-test` 스킬의 몫이다 — 이 스킬에서 다시 다루지 않는다. 다만 이 스킬이 정의하는 테스트 설계 기법(`test-case-design.md`)과 Doxygen 목적 설명 규칙(`test-doxygen-convention.md`)은 두 스킬이 공통으로 재사용하는 원본이다.

## 핵심 원칙

**테스트를 먼저 쓴다. 실패하는 것을 본다. 통과하는 최소 코드를 쓴다.**

테스트가 실패하는 것을 직접 보지 않았다면, 그 테스트가 올바른 것을 검증하는지 알 수 없다.

**규칙의 문구를 어기는 것은 규칙의 취지를 어기는 것이다.** — "이번 한 번만 TDD를 건너뛰자"는 생각이 든다면, 그것은 정당화가 아니라 회피다.

## 철칙 (The Iron Law)

```
실패하는 테스트 없이 프로덕션 코드를 작성하지 않는다.
```

테스트보다 코드를 먼저 썼다면? 그 코드는 삭제하고 처음부터 다시 시작한다.

**예외 없음**:
- "참고용"으로 남겨두지 않는다
- 테스트를 쓰면서 그 코드를 "적당히 손봐서" 재사용하지 않는다
- 쳐다보지도 않는다
- 삭제는 삭제다 — 테스트로부터 완전히 새로 구현한다

## 0단계 — 입력 확인 (이 프로젝트의 선행 조건)
- 구현 대상 소프트웨어 단위의 상세설계(`detailed-design` 스킬 산출물)를 확인한다: 단위 인터페이스(파라미터, 방향, 데이터 타입, 유효범위, 물리단위), 사전/사후조건, 오류처리 방식, 동적 측면(호출순서).
- 상세설계가 없거나 불완전하면(예: 유효범위 미기재) 구현을 시작하지 않는다 — 먼저 상세설계를 보완하도록 사용자에게 확인한다.
- `references/template.md`(WP_Templates `TPL-SWE4-001`/`TPL-SWE4-002` 확정 양식)를 확인한다 — 이 스킬의 실제 산출물(Python 테스트 코드)과 별도로, 조직이 요구하는 형식화된 단위시험 명세서·결과서(xlsx)도 함께 채운다.

## Red-Green-Refactor 사이클

```
[RED: 실패하는 테스트 작성] → [Red 검증: 올바른 이유로 실패하는가?]
   → (아니오: 테스트 수정 후 재확인) → (예) → [GREEN: 최소 구현]
   → [Green 검증: 통과하고 다른 테스트도 안 깨지는가?]
   → (아니오: 코드 수정) → (예) → [REFACTOR: 품질게이트 실측하며 정리]
   → [Green 유지 재확인] → 다음 테스트로 반복
```

### RED — 실패하는 테스트 먼저 작성

하나의 행위(behavior)만 검증하는 최소 테스트를 작성한다. **이 프로젝트에서는 아래 3가지를 테스트 docstring에 반드시 포함한다** — `references/test-doxygen-convention.md`의 형식을 그대로 따른다:

1. **목적(@brief)**: Doxygen 형식으로, 이 테스트가 무엇을 검증하는지 한 문장으로.
2. **사용 기법**: 경계값분석/동등분할/오류추측/상태기반테스트/회귀재현 중 무엇을 근거로 이 테스트를 만들었는지(`references/test-case-design.md` 참조).
3. **케이스 성격(긍정/부정)**: 정상 동작을 검증하는 긍정(Positive) 케이스인지, 오류·예외·경계 위반을 검증하는 부정(Negative) 케이스인지.

테스트 작성 전, 스스로에게 묻는다: **"어떤 프로덕션 코드 변경이 이 테스트를 실패하게 만드는가 — 그리고 그것은 버그인가, 설계 결정인가?"** 이 질문에 답할 수 없으면 테스트를 다시 설계한다(`references/writing-good-tests.md`의 "깨짐을 이름 붙이기" 원칙).

<좋은 예>
```python
def test_retriesFailedOperation_succeedsOnThirdAttempt(self):
    """!
    @brief 실패하는 오퍼레이션을 3회까지 재시도하면 성공을 반환하는지 검증한다.
    @testtype 긍정(Positive)
    @technique 동등분할(Equivalence Partitioning) — "3회 이내 성공" 대표값 사용
    """
    attempts = {"count": 0}
    def operation():
        attempts["count"] += 1
        if attempts["count"] < 3:
            raise RuntimeError("fail")
        return "success"

    result = retryOperation(operation)

    self.assertEqual(result, "success")
    self.assertEqual(attempts["count"], 3)
```
명확한 이름, 실제 코드로 검증, 하나의 행위만 다룸.
</좋은 예>

<나쁜 예>
```python
def test_retryWorks(self):
    mockOp = Mock(side_effect=[RuntimeError(), RuntimeError(), "success"])
    retryOperation(mockOp)
    self.assertEqual(mockOp.call_count, 3)
```
이름이 모호하고, 실제 코드가 아니라 mock의 호출 횟수만 검증한다.
</나쁜 예>

**요구사항**: 하나의 행위, 명확한 이름, 실제 코드 사용(불가피한 경우가 아니면 mock 지양 — `writing-good-tests.md` 참조), 기대값은 코드 스스로가 아니라 손으로 도출.

### Red 검증 — 실패를 직접 확인 (필수, 절대 생략 금지)

```
python -m unittest tests.test_foo.TestFoo.test_belowMinBoundary_raisesValueError
```

확인할 것:
- 테스트가 **실패**하는가 (에러가 아니라 실패, 즉 assert 실패인지)
- 실패 메시지가 예상한 것인가
- "기능이 아직 없어서" 실패하는 것이 맞는가(오탈자·설정 오류로 인한 실패가 아닌지)

**테스트가 통과해버리면?** 이미 존재하는 동작을 테스트하고 있는 것이다 — 테스트를 다시 본다.
**테스트가 에러(예외로 죽음)를 내면?** 에러를 고치고 "실패"가 나올 때까지 다시 실행한다.

### GREEN — 통과시키는 최소 구현

테스트를 통과시키는 데 필요한 최소한의 코드만 작성한다. 아직 요청받지 않은 옵션·설정·유연성을 미리 만들지 않는다(YAGNI). 이 시점에도 `coding` 스킬의 네이밍 규칙(3글자 이상, 카멜케이스)은 처음부터 지킨다.

### Green 검증 — 통과를 직접 확인 (필수)

```
python -m unittest discover -s tests
```

확인할 것: 이 테스트가 통과하는가, 다른 기존 테스트가 깨지지 않았는가, 출력이 깨끗한가(경고·에러 없음).

**테스트가 실패하면?** 테스트가 아니라 코드를 고친다. **다른 테스트가 깨지면?** 지금 바로 고친다.

### REFACTOR — 품질게이트를 실측하며 정리

Green 상태에서만 리팩터링한다. 새로운 동작을 추가하지 않는다.
- 중복 제거, 이름 정리, 헬퍼 추출.
- **`coding` 스킬의 품질지표를 오픈소스 도구로 실제 측정**한다(함수 라인수 ≤50, 순환복잡도 ≤10, 중복 ≤7라인, Doxygen 주석 20% 이상, 네이밍 규칙) — `coding` 스킬의 `references/opensource-tooling.md` 명령을 그대로 사용한다. 느낌으로 "지켰다"고 넘어가지 않는다.
- 리팩터링 후 반드시 테스트를 재실행해 Green을 재확인한다.

### 반복
다음 실패하는 테스트로 넘어가 사이클을 반복한다.

## 좋은 테스트의 조건

| 기준 | 좋음 | 나쁨 |
|------|------|------|
| **최소성** | 한 가지만 검증. 이름에 "그리고"가 들어가면 분리 | `test_validatesEmailAndDomainAndWhitespace` |
| **명확성** | 이름이 행위를 설명 | `test_case1` |
| **의도 표현** | 원하는 API를 그대로 보여줌 | 코드가 무엇을 해야 하는지 감춤 |

테스트를 쓰거나 고칠 때는 `references/writing-good-tests.md`를 반드시 읽는다 — 테스트가 정직함을 유지하기 위한 규칙(기대값을 코드 스스로 계산하지 않기, mock 자체를 검증하지 않기, 테스트 전용 코드는 테스트 유틸리티에만 두기, mock하기 전 의존성의 부작용을 먼저 이해하기)을 담고 있다.

## 흔한 합리화와 그 실체

| 핑계 | 실체 |
|------|------|
| "너무 간단해서 테스트할 필요 없다" | 간단한 코드도 깨진다. 테스트는 30초면 된다. |
| "나중에 테스트 쓸 것이다" | 나중에 쓴 테스트는 바로 통과한다 — 그건 아무것도 증명하지 못한다는 뜻이다. 잘못된 것을 테스트하거나, 행위 대신 구현을 테스트하거나, 잊어버린 경계 케이스를 놓칠 수 있다. 실패를 본 적이 없으니 버그를 잡을 수 있다는 것도 증명한 적이 없다. |
| "테스트 먼저나 나중이나 목표는 같다(의식이 아니라 정신이 중요)" | 나중에 쓴 테스트는 "이게 뭘 하지?"에 답하고, 먼저 쓴 테스트는 "이게 뭘 해야 하지?"에 답한다. 나중에 쓴 테스트는 이미 짠 코드에 편향된다 — 기억나는 케이스만 확인하지, 발견했어야 할 케이스는 놓친다. |
| "이미 수동으로 테스트해봤다" | 수동 테스트는 즉흥적이다. 무엇을 확인했는지 기록이 없고, 코드가 바뀌면 재실행할 수 없고, 압박 속에서 케이스를 빼먹기 쉽다. |
| "몇 시간 들인 코드를 지우는 건 낭비다" | 매몰비용의 오류다 — 그 시간은 이미 썼다. 진짜 선택은: TDD로 다시 쓰기(높은 신뢰) vs. 그대로 두고 테스트만 나중에 붙이기(낮은 신뢰, 버그 가능성 높음). |
| "참고용으로 남기고 테스트부터 쓰겠다" | 결국 그 코드를 "적당히" 손보게 된다 — 그건 나중에 테스트 쓰는 것과 같다. |
| "테스트하기 어려운 건 설계가 불명확해서다" | 테스트가 하는 말을 들어라. 테스트하기 어려우면 쓰기도 어려운 것이다. |
| "TDD는 느리다" | TDD가 실용적인 길이다 — 커밋 전에 버그를 잡고, 회귀를 막고, 두려움 없이 리팩터링하게 해준다. "실용적" 지름길은 결국 프로덕션에서 디버깅하는 것 — 더 느리다. |

## 위험 신호 — 발견하면 멈추고 다시 시작

- 테스트보다 코드가 먼저 있다
- 구현 후에 테스트를 만들었다
- 테스트가 바로 통과한다
- 왜 실패했는지 설명할 수 없다
- 테스트를 "나중에" 추가했다
- "이번 한 번만"이라고 합리화하고 있다
- "이미 수동으로 테스트했다"
- "참고용으로 남기겠다" 또는 "기존 코드를 적당히 손보겠다"

**이 중 하나라도 해당하면: 코드를 삭제하고 TDD로 처음부터 다시 시작한다.**

## 검증 체크리스트 (완료로 표시하기 전)

- [ ] 모든 신규 함수/메서드에 테스트가 있다
- [ ] 각 테스트가 구현 전에 실패하는 것을 직접 확인했다
- [ ] 각 테스트가 예상한 이유로 실패했다(기능 없음 때문이지, 오탈자 때문이 아님)
- [ ] 각 테스트를 통과시키는 최소 코드를 작성했다
- [ ] 모든 테스트가 통과한다
- [ ] 출력이 깨끗하다(에러·경고 없음)
- [ ] 실제 코드를 사용했다(불가피한 경우만 mock)
- [ ] 경계 케이스와 오류 케이스를 다뤘다
- [ ] 모든 테스트에 목적(@brief)·기법·긍정/부정 표시가 있다(`test-doxygen-convention.md`)
- [ ] `coding` 스킬의 품질지표를 도구로 실측했다
- [ ] 소스코드 ↔ 상세설계 추적 링크를 갱신했다

체크할 수 없는 항목이 있으면 TDD를 건너뛴 것이다 — 처음부터 다시 한다.

## 막혔을 때

| 문제 | 해결 |
|------|------|
| 테스트를 어떻게 써야 할지 모르겠다 | 원하는 API를 먼저 적어본다. assert부터 쓴다. 상세설계를 다시 확인한다. |
| 테스트가 너무 복잡하다 | 설계가 너무 복잡한 것이다. 인터페이스를 단순화한다. |
| 모든 것을 mock해야 한다 | 코드가 너무 결합되어 있다. 의존성 주입을 사용한다(`architecture-designer`의 DIP 원칙). |
| 테스트 준비(setup)가 방대하다 | 헬퍼로 추출한다. 그래도 복잡하면 설계를 단순화한다. |

## 디버깅 통합
버그를 발견했는가? 그 버그를 재현하는 실패하는 테스트를 먼저 쓴다. TDD 사이클을 따른다. 테스트가 수정을 증명하고 회귀를 막는다. 테스트 없이 버그를 고치지 않는다.

## 추적성 갱신 (이 프로젝트 고유)
`detailed-design` 스킬의 `traceability-continuation.md`에 정의된 "소스코드 ↔ 상세설계" 링크를 실제 코드 위치(파일경로::함수명)로 채운다. 테스트 코드도 어느 단위·요구사항을 검증하는지 함께 기록한다.

## 최종 규칙

```
프로덕션 코드 → 테스트가 존재하고 먼저 실패했다
그렇지 않으면 → TDD가 아니다
```

예외는 사용자의 명시적 허락 없이는 없다.
