# 좋은 테스트 작성 규칙

> 출처: [obra/superpowers](https://github.com/obra/superpowers) `test-driven-development/writing-good-tests.md`(MIT License)를 Python 환경에 맞게 각색.

**이 파일을 읽어야 할 때**: 테스트를 작성하거나 수정할 때, mock을 추가할 때, 테스트용 정리(cleanup)/헬퍼 메서드를 추가할 때.

## 개요

테스트는 특정한 깨짐(break)을 잡기 위해 존재한다. 두 가지 원칙이 모든 것을 지배한다:

```
1. 모든 테스트는 자신이 잡아내는 깨짐의 이름을 댈 수 있어야 한다
2. 모든 테스트는 실제 코드를 실행해야 한다
```

엄격한 TDD는 이 둘을 자연스럽게 만족시킨다 — 먼저 쓰고 실제 코드에 대해 실패하는 것을 본 테스트는 이미 "실패할 수 있음"을 증명한 것이고, 실제 의존성이 느리거나 외부 자원일 때만 mock을 쓸 자격을 얻는다.

## 원칙 1: 깨짐에 이름 붙이기

테스트 본문을 쓰기 전에 답한다: **어떤 프로덕션 코드 변경이 이 테스트를 실패하게 만드는가 — 그리고 그것은 버그인가, 설계 결정인가?** 테스트는 잘못된 분기, 누락된 부작용, 잘못된 인자, 경계 케이스, 깨진 계약을 잡아낼 때 존재 가치가 있다.

**기대값은 독립적으로 도출한다.** 리터럴 값과 손으로 확인한 픽스처를 사용한다 — 테이블 기반 테스트에 리터럴 `want` 값을 쓰는 것을 선호한다. 검증 대상 코드(또는 그 헬퍼)로 계산한 기대값은 그 코드가 무엇을 하든 항상 통과한다:

```python
# ❌ 거울 assert: 같은 함수로 양쪽을 계산 — 항상 참
expected = buildSearchQuery({"tag": "urgent"})
self.assertEqual(buildSearchQuery({"tag": "urgent"}), expected)

# ✅ 손으로 도출한 리터럴
self.assertEqual(buildSearchQuery({"tag": "urgent"}), 'tag:"urgent"')
```

**변경 감지기를 만들지 않는다.** 의도적인 설계 결정만 실패하게 만드는 테스트(상수값, 정확한 메시지 문구, 내부 구조)는 재설계할 때만 발동하고 정작 버그에는 잠들어 있다. 결정 자체가 아니라 그 결정에 의존하는 행위를 테스트한다: `self.assertEqual(MAX_RETRIES, 5)`가 아니라 "실패하는 호출이 5번 재시도되고, 6번째 시도는 일어나지 않는다."

**행위를 테스트하지, 텍스트를 테스트하지 않는다.** 스크립트·스킬·설정 파일이 특정 문구를 포함하는지 assert하는 것은 소스가 소스라는 것만 증명한다. 통제된 입력으로 스크립트를 실행하고 출력·부작용·종료코드를 assert한다.

**당신의 코드를 테스트하지, 프레임워크를 테스트하지 않는다.** 코드가 경계에서 맺는 계약(등록하는 라우트, 발행하는 쿼리, 만들어내는 페이로드)을 테스트한다. 표준 라이브러리·서드파티 라이브러리 자체의 동작은 그 라이브러리의 유지관리자가 테스트할 몫이다.

### 게이트 함수 (테스트 작성 전 자가점검)
```
테스트 본문을 쓰기 전에:
  이 테스트를 실패하게 만드는 프로덕션 코드 변경을 이름 붙여본다.

  이름을 붙일 수 없다        → 관측 가능한 행위 중심으로 재설계
  "소스 텍스트가 바뀜"       → 산출물을 실행하고 그 효과를 assert
  의도적 결정만 실패시킴     → 변경 감지기다; 그 결정에 의존하는 행위를 테스트

  기대값이 검증 대상 코드 없이 도출되었는지 확인한다.
  만약 검증 대상 코드나 그 헬퍼를 재사용했다면:
    리터럴 값이나 손으로 확인한 픽스처로 교체한다
```

## 원칙 2: 실제 코드를 실행하기

**mock은 그 자체로 assert 대상이 되지 않는다.** mock이 있으면 통과하고 없으면 실패하는 assert는 컴포넌트에 대해 아무것도 말해주지 않는다. 실제 컴포넌트의 행위를 assert한다 — mock을 확인하고 싶다면 mock을 풀거나 그 assert를 삭제한다.

```python
# ✅ 실제 행위
self.assertTrue(page.hasElementWithRole("navigation"))

# ❌ mock 존재 여부
self.assertTrue(page.hasTestId("sidebar-mock"))
```

**적절한 수준에서 mock한다.** 실제 메서드의 모든 부작용을 먼저 파악한 뒤, 느리거나 외부 자원인 연산만 대체하고 테스트가 의존하는 나머지는 실제로 둔다. 확신이 없으면 먼저 실제 구현으로 테스트를 실행해 실제로 무엇이 필요한지 관찰한다.

**더블(double)을 구체적으로 만든다.** 인자·호출 횟수·순서가 계약의 일부라면 그것을 assert한다 — 아무거나 받아주는 fake는 아무것도 검증하지 못한다. 성공/오류/비정상 케이스마다 각각의 픽스처나 spy를 둔다.

**mock 응답은 실제 구조를 완전히 반영한다.** 테스트가 읽는 필드만이 아니라 실제로 존재하는 모든 문서화된 필드를 mock한다. 부분적인 mock은 하위 코드가 누락된 필드를 읽을 때 조용히 실패한다 — 테스트는 통과하는데 통합은 깨진다.

**프로덕션 클래스에는 프로덕션 메서드만 둔다.** 테스트만 필요로 하는 정리(cleanup) 코드는 테스트 유틸리티에 두지, 프로덕션 클래스의 `destroy()` 같은 메서드로 만들지 않는다.

**복잡한 mock보다 실제 컴포넌트를 우선한다.** mock 설정이 테스트 로직보다 커지거나, mock이 실제 컴포넌트가 가진 메서드를 놓치거나, mock이 바뀔 때마다 테스트가 깨진다면 실제 컴포넌트를 쓰는 통합 테스트로 전환한다.

### 게이트 함수 (mock/헬퍼 추가 전 자가점검)
```
mock이나 테스트 헬퍼를 추가하기 전에:
  실제 메서드의 부작용을 나열하고, 테스트가 의존하는 것은 실제로 두고
  느리거나 외부 자원인 수준만 mock한다.

  mock 응답이 실제 구조를 완전히 반영하는가.

  테스트에서만 호출되는 메서드는 테스트 유틸리티에 있는가(프로덕션 클래스가 아님).

  mock 자체를 assert하려는 중인가?
    mock을 풀거나 그 assert를 삭제한다.
```

## 테스트는 구현과 함께 완성된다
TDD 사이클(실패하는 테스트 → 최소 구현 → 리팩터링)이 곧 "완료"의 의미다. 그 행위가 필요로 하는 테스트만 만든다 — 사소한 코드와 사람이 읽을 산문(prose)에는 테스트를 붙이지 않는다. 절차를 만족시키기 위해 쓴 테스트는 유지보수 부담만 영원히 남긴다.

## 변이 확인 (Mutation Check)
끝내기 전에, 머릿속으로 프로덕션 코드를 변이(mutate)시켜본다. 현실적인 변이마다 최소 하나의 테스트가 실패해야 한다:
- 잘못된 상수나 인자
- 잘못된 분기 처리
- 누락된 상태변경·부작용
- 빈 값 또는 기본값 반환
- 0, 빈 값, null, 권한 없음, 잘못된 형식 입력에 대한 검증 누락

어떤 변이도 잡아내지 못하는 테스트는 그 행위가 보호받지 못하고 있거나, 테스트가 동어반복이라는 뜻이다.

## 빠른 참조표

| 이럴 때... | 이렇게 한다 |
|-----------|-------------|
| 테스트를 쓸 때 | 그것이 잡아내는 깨짐의 이름을 댄다 — 설계 결정이 아니라 버그 |
| 기대값을 만들 때 | 손으로 도출한다 — 검증 대상 코드로 계산하지 않는다 |
| 스크립트/문서를 테스트할 때 | 실행하거나 그 소비자를 검증한다 — 텍스트를 grep하지 않는다 |
| 의존성 테스트가 하고 싶을 때 | 그들의 문서화된 메커니즘이 아니라 우리 코드와의 경계 계약을 테스트한다 |
| mock된 요소를 assert하고 싶을 때 | 실제 컴포넌트를 테스트하거나 mock을 푼다 |
| 메서드를 mock하려 할 때 | 부작용을 먼저 파악하고, 느리거나 외부 자원인 수준만 mock한다 |
| mock 응답을 만들 때 | 실제 구조를 완전히 반영한다 |
| 테스트 전용 정리 코드가 필요할 때 | 테스트 유틸리티에 둔다 |
| mock 설정이 비대해질 때 | 실제 컴포넌트를 쓰는 통합 테스트로 전환한다 |
| 테스트 파일을 끝낼 때 | 변이 확인을 수행한다 |

## 경고 신호
- 준비(setup)와 assert가 같은 객체를 공유해 항상 같음을 보장한다
- 예외나 충돌, selector 누락으로만 테스트가 실패할 수 있다
- 의도적 변경마다 항상 실패하고, 실수로 인한 깨짐에는 절대 실패하지 않는다
- 기대값이 반복문·빌더·헬퍼 뒤에 숨겨져 있다
- 소스 텍스트를 grep하거나, 제거된 심볼이 계속 없는지만 assert한다
- 프레임워크만 남아도 여전히 통과할 테스트다
- 커버리지만을 위해 존재하고 부작용·결과를 확인하지 않는다
- `*-mock` 테스트 ID를 assert하거나, mock을 제거하면 실패한다
- 테스트 파일에서만 호출되는 메서드가 있다
- mock 설정이 테스트의 절반 이상을 차지하거나, 왜 필요한지 설명할 수 없다
- "혹시 몰라서" mock한다
