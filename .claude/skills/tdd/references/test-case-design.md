# 테스트 케이스 설계 기법 (Red 단계에서 사용)

`detailed-design` 스킬 산출물의 단위 인터페이스(유효범위·물리단위·오류처리·사전/사후조건)를 테스트 케이스로 변환하는 방법이다. **아래 기법 중 무엇을 사용했는지는 반드시 해당 테스트의 Doxygen 주석 `@technique` 태그에 그대로 기록한다(`test-doxygen-convention.md` 참조) — 기법을 고르고 끝내지 말고, 그 선택을 테스트 코드에 남긴다.**

## 경계값 분석 (Boundary Value Analysis)
유효범위 `min..max`가 주어지면 최소 아래 5개 값을 후보로 검토한다:
- `min` (최소 경계) — 긍정 케이스
- `min - 1`(또는 해당 타입에서 가장 가까운 하위 값, 범위 미만) — 부정 케이스
- `max` (최대 경계) — 긍정 케이스
- `max + 1`(범위 초과) — 부정 케이스
- 범위 내 대표값(정상 케이스) — 긍정 케이스

물리단위가 있는 값이면 단위 변환 실수도 함께 점검한다(예: ms와 s 혼동으로 인한 자릿수 오류).

## 동등 분할 (Equivalence Partitioning)
입력이 여러 카테고리(예: 정상/특수값/오류)로 나뉘면 각 카테고리에서 대표값 하나씩만 뽑아 테스트 수를 합리적으로 줄인다 — 모든 값을 다 테스트할 필요는 없다. 정상 카테고리는 긍정 케이스, 오류 카테고리는 부정 케이스로 표시한다.

## 오류 추측 (Error Guessing) + 상세설계의 오류처리 명세
`detailed-design`의 "오류·예외 처리" 항목에 정의된 대로(예외 발생/클램핑/오류코드 반환) 정확히 그 동작을 테스트한다 — 설계에 없는 임의의 오류처리를 가정해 테스트하지 않는다. 이 기법으로 만든 테스트는 대부분 부정 케이스다.

## 상태 기반 테스트 (동적 측면이 있는 단위)
상세설계에 상태 전이가 정의되어 있으면(`detailed-design`의 동적 측면), 각 상태 전이 경로마다 최소 1개의 테스트를 작성한다: 정상 전이(긍정), 허용되지 않는 전이 시도(부정 — 거부되는지 확인).

## 회귀재현 (Regression)
버그를 수정할 때는 그 버그를 재현하는 실패하는 테스트를 먼저 쓴다(`tdd` 스킬 SKILL.md의 "디버깅 통합" 참조). 이 기법으로 만든 테스트는 부정 케이스로 표시하고, 가능하면 이슈/버그 번호를 `@brief`에 남긴다.

## 사전조건/사후조건 테스트
- 사전조건 위반 시 설계된 동작(예외/오류코드)이 실제로 발생하는지 테스트한다.
- 사후조건은 정상 케이스 테스트의 assert 대상이 된다 — "이 조건을 만족하는 출력을 낸다"가 곧 사후조건 검증이다.

## 테스트 케이스 수 판단 기준
- 위 기법을 다 적용해도 테스트 수가 지나치게 많아지면(예: 파라미터 조합 폭발), 동등 분할로 대표 조합만 추리고 그 판단 근거를 기록한다.
- 반대로 테스트가 정상 케이스 하나뿐이라면 Red 단계가 불충분한 것이다 — 최소한 경계값과 오류 케이스가 함께 있어야 한다(즉, 긍정·부정 케이스가 모두 있어야 한다).

## 기법·케이스 성격 기록 요약
| 기법 | 주로 만드는 케이스 성격 |
|------|--------------------------|
| 경계값 분석 | 긍정(경계 내) + 부정(경계 밖) 모두 |
| 동등 분할 | 카테고리에 따라 긍정/부정 모두 가능 |
| 오류 추측 | 대부분 부정 |
| 상태 기반 테스트 | 긍정(허용 전이) + 부정(금지 전이) |
| 회귀재현 | 부정(버그였던 케이스) |

이 표의 매핑을 그대로 `test-doxygen-convention.md`의 `@technique`/`@testtype` 태그 값으로 옮겨 적는다.
