# 요구사항 분석 스킬 (ISO 26262 · A-SPICE 4.1 정합)

지정된 템플릿에 맞춰, ISO 26262와 A-SPICE 4.1(주로 SYS.1 요구사항 도출, SYS.2 시스템 요구사항 분석, SWE.1 소프트웨어 요구사항 분석)을 만족하는 요구사항 산출물을 작성·검토한다. 이 스킬의 목표는 단순히 "요구사항 문장을 쓰는 것"이 아니라, 아래 6가지 품질 게이트를 모두 통과하는 요구사항 집합을 만드는 것이다.

1. **템플릿 준수** — 사용자가 지정한 템플릿의 필드·양식을 그대로 따른다.
2. **표준 준수** — ISO 26262-8 Clause 6(요구사항 명세) 및 A-SPICE 4.1 SYS.1/SYS.2/SWE.1의 요구사항 특성을 충족한다.
3. **기능요구사항의 다이어그램화** — UML/SysML로 표현 가능해야 한다.
4. **비기능요구사항의 ISO 25010 정합** — 품질특성/부특성으로 분류하고, 실행 가능한 검증방안을 함께 제시한다.
5. **이해가능성** — 모호하지 않고 사람이 읽고 바로 이해할 수 있어야 한다.
6. **양방향 추적성과 일관성** — 정의된 방식대로 상하위 산출물과 링크되고, 요구사항 간 모순이 없어야 한다.

정확한 체크리스트와 근거 표준 원문은 `references/`에 있으며, 단계별로 필요한 파일을 읽어서 적용한다.

## 0단계 — 템플릿 확인 (선행 조건)

`references/template.md`를 먼저 읽는다.

- 이 파일이 **"임시(INTERIM) 템플릿"**으로 표시되어 있다면: 사용자가 실제 템플릿을 아직 제공하지 않은 상태다. 임시 템플릿으로 초안을 작성하는 것은 가능하지만, 결과물 상단에 "⚠ 사용자 지정 템플릿 미수령 — 임시 템플릿 기준으로 작성됨. 실제 템플릿 수령 시 필드 재정렬 필요"를 반드시 명시한다.
- 사용자가 실제 템플릿을 채팅/파일로 제공하면, `references/template.md`를 그 내용으로 갱신(덮어쓰기)하고 "임시" 표시를 제거한 뒤 이후 작업부터는 정식 템플릿으로 간주한다.
- 템플릿 필드와 아래 단계(추적성 필드, 검증방안 필드, 다이어그램 참조 필드 등)가 어떻게 매핑되는지 확인한다. 템플릿에 없는 컬럼이 이 스킬에서 필수로 요구하는 경우(예: 양방향 추적 링크), 템플릿을 임의로 바꾸지 말고 사용자에게 필드 추가 여부를 확인한다.

## 절차

### 1단계 — 범위와 유형 분류
- 요구사항 레벨 결정: 이해관계자 요구사항(Stakeholder, SYS.1) / 시스템 요구사항(SYS.2) / 소프트웨어 요구사항(SWE.1) 중 어디를 작성하는지 확인.
- 요구사항을 기능요구사항(FR)과 비기능요구사항(NFR)으로 1차 분류한다. 하나의 요구사항 문장에 기능과 품질기준이 섞여 있으면 분리한다(원자성 확보, `references/iso26262-requirements-criteria.md` 참조).

### 2단계 — 기능요구사항(FR) 작성 및 다이어그램화
- 각 FR은 템플릿 필드(ID, 제목, 설명, 출처, 수용기준 등)를 채운다.
- `references/uml-sysml-notation.md`를 참고해 요구사항의 성격에 맞는 다이어그램 유형을 선택하고 작성한다(유스케이스/액티비티/시퀀스/상태기계/요구사항 다이어그램/블록정의·내부블록 다이어그램). 다이어그램은 텍스트 요구사항을 대체하지 않고 보완한다 — 다이어그램 요소에 반드시 대응하는 요구사항 ID를 라벨로 표기해 추적성을 유지한다.
- 다이어그램 소스는 버전관리·리뷰가 가능한 텍스트 기반(PlantUML/Mermaid 등)으로 작성하는 것을 기본으로 한다.

### 3단계 — 비기능요구사항(NFR) 작성 및 검증방안
- `references/iso25010-nfr-checklist.md`의 9개 품질특성(기능적합성 제외 시 8개: 성능효율성, 호환성, 상호작용역량, 신뢰성, 보안성, 유지보수성, 유연성, 안전성) 중 해당 특성/부특성을 태깅한다.
- 각 NFR은 정량적 기준(수치+단위+조건)으로 작성한다. "빠르게", "적절히" 같은 모호한 형용사를 쓰지 않는다.
- 검증방안은 **실행 가능한 것만** 제시한다. 아래 기준으로 자체 검토한다:
  - 프로젝트가 실제로 보유했거나 확보 가능한 도구/환경/데이터로 수행 가능한가?
  - 유한한 시간·자원 내에 종료되는가(전수조사나 무한 반복을 요구하지 않는가)?
  - 결과가 통과/실패를 객관적으로 판정할 수 있는 형태인가(측정 가능한 임계값)?
  - 위 세 질문 중 하나라도 "아니오"이면 검증방안을 실행 가능한 대안(대표 샘플링, 벤치마크, 정적분석, 시뮬레이션, 코드리뷰, 프로토타입 측정 등)으로 다시 설계한다.
  - 지양해야 할 예시와 대안은 `references/iso25010-nfr-checklist.md` 하단 표를 참고한다.

### 4단계 — 이해가능성 검토
`references/iso26262-requirements-criteria.md`의 체크리스트(고유식별, 비모호성, 이해가능성, 원자성, 완전성, 일관성, 실현가능성, 검증가능성)로 모든 요구사항(FR/NFR 공통)을 재검토한다. 특히:
- 능동태·단문 사용, 대명사("그것", "이것") 대신 명시적 대상 지칭.
- 약어·전문용어는 최초 등장 시 정의(용어집이 있으면 그것을 따르고, 없으면 이번 산출물에 용어집 섹션을 만든다).
- 해당 분야 배경지식이 없는 리뷰어도 한 번 읽고 재해석 없이 이해할 수 있는지 자체 점검(가능하면 실제로 사용자에게 확인을 구한다).

### 5단계 — 양방향 추적성 확보
`references/traceability-scheme.md`에 정의된 ID 체계와 링크 방식을 그대로 사용한다.
- 모든 요구사항에 고유 ID를 부여한다.
- 상위 추적(이 요구사항이 어떤 상위 요구/니즈에서 파생됐는지)과 하위 추적(이 요구사항이 어떤 아키텍처/설계/테스트케이스/코드에 반영됐는지) 링크를 실제로 채운다 — 링크 필드를 비워두고 "나중에 채운다"고 미루지 않는다. 하위 산출물이 아직 없으면 "미할당(미배정)"으로 명시적으로 표기하고, 산출물이 생기는 시점에 갱신한다.
- 추적매트릭스(`traceability-scheme.md`에서 정한 위치)를 함께 갱신한다.
- 고아 요구사항(상위 근거 없음)과 커버리지 갭(하위 산출물 없음)을 점검해 결과에 명시한다.

### 6단계 — 일관성 점검
- 같은 대상(기능/인터페이스/파라미터)에 대해 서로 다른 요구사항이 상충하는 값·조건을 요구하지 않는지 교차 검토한다.
- 용어·단위·명명규칙이 문서 전체에서 통일되어 있는지 확인한다(용어집과 대조).
- 신규/변경 요구사항이 기존 요구사항 집합과 충돌하면, 충돌 내용과 해결(변경/폐기/우선순위) 방안을 명시적으로 기록한다.

### 7단계 — A-SPICE 산출물 매핑
작성한 요구사항이 어떤 A-SPICE 출력 정보항목에 해당하는지 표기한다(SYS.1/SYS.2: 17-00 Requirement, 17-54 Requirement Attribute, 15-51 Analysis Results, 13-51 Consistency Evidence, 13-52 Communication Evidence 등). 상세 목록은 `aspice-auditor` 스킬의 `references/process-work-products.md`를 함께 참고한다(이미 프로젝트에 설치되어 있다면).

## 출력 형식
템플릿(0단계) 필드를 기본으로 하되, 없으면 아래를 최소 구성으로 쓴다:

```
## <요구사항 ID> — <제목>

- 유형: 기능(FR) / 비기능(NFR: <ISO25010 특성/부특성>)
- 레벨: 이해관계자 / 시스템 / 소프트웨어
- 출처(근거): ...
- 설명: (모호하지 않고 원자적인 서술)
- 수용기준 / 정량 기준: ...
- 검증방안: (실행 가능한 방법 — 테스트/분석/리뷰/시뮬레이션 등 구체적으로)
- 다이어그램(FR인 경우): <다이어그램 유형> — <파일 경로/링크>, 요구사항 ID 라벨 포함 여부
- 상위 추적: <부모 ID 또는 "미배정">
- 하위 추적: <자식 ID 목록 또는 "미배정">
- 상태: 초안 / 합의됨 / 변경중
```

마지막에 다음을 요약해 보고한다: 총 요구사항 수, FR/NFR 비율, 다이어그램 첨부 여부, 추적성 커버리지(고아/갭 유무), 일관성 이슈 유무, 템플릿 수령 여부(임시/정식).

## 주의사항
- 실행 불가능한 검증방안(예: "모든 사용자가 만족해야 한다", "무한 입력 조합에 대해 오류가 없어야 한다")은 절대 제시하지 않는다. 반드시 유한하고 측정 가능한 대안으로 재작성한다.
- 다이어그램은 요구사항의 이해를 돕기 위한 것이지, 다이어그램이 있다고 텍스트 요구사항의 모호성이 면제되지는 않는다.
- 추적 링크는 "존재"만으로 충분하지 않다 — A-SPICE 4.1 원문(SYS.2 Note 7, SWE.1 Note 11)도 "추적 링크의 존재 자체가 정보의 일관성을 의미하지는 않는다"고 명시한다. 링크된 두 산출물의 내용이 실제로 부합하는지 확인한다.
