# 비기능요구사항(NFR) 작성 체크리스트 — ISO/IEC 25010:2023 품질특성

> 출처: ISO/IEC 25010:2023 제품 품질 모델(9개 최상위 특성). 2023년 개정판에서 "안전성(Safety)"이 신설되었고, 기존 "사용성(Usability)"은 "상호작용역량(Interaction Capability)"으로, "이식성(Portability)"은 "유연성(Flexibility)"으로 개편되었다. **기능적합성(Functional Suitability)**은 기능요구사항(FR) 영역이므로 이 체크리스트에서는 참고만 하고, 나머지 8개를 비기능요구사항(NFR) 분류 기준으로 사용한다.

각 특성마다: 정의 → 하위특성 → 요구사항 작성 패턴(정량 기준 예시) → 실행 가능한 검증방안 예시 → 지양할 검증방안(비실행성) 순으로 정리했다.

## 1. 성능효율성 (Performance Efficiency)
- 하위특성: 시간반응성(Time behavior), 자원활용성(Resource utilization), 용량(Capacity)
- 작성 패턴: "시스템은 <조건> 하에서 <동작>을 <시간/자원 임계값> 이내에 완료해야 한다."
- 실행 가능한 검증방안: 부하테스트 도구(JMeter 등)로 N동시사용자 시나리오 측정, 프로파일러로 CPU/메모리 사용량 측정, 정해진 데이터셋으로 처리량 벤치마크.
- 지양할 예시: "어떤 상황에서도 항상 빨라야 한다" → 조건·수치 없는 무한 범위 요구는 검증 불가.

## 2. 호환성 (Compatibility)
- 하위특성: 공존성(Co-existence), 상호운용성(Interoperability)
- 작성 패턴: "시스템은 <특정 환경/버전>과 <특정 인터페이스/프로토콜>로 상호운용되어야 한다."
- 실행 가능한 검증방안: 지정된 타 시스템/버전 조합으로 통합테스트, 프로토콜 준수 여부 정적 검증(스키마 검증 등).
- 지양할 예시: "모든 기존 및 미래 시스템과 호환되어야 한다" → 대상이 무한하여 검증 불가. 대상 시스템 목록을 명시해야 한다.

## 3. 상호작용역량 (Interaction Capability, 구 사용성)
- 하위특성: 적절성 인식성, 학습성, 운용성, 사용자 오류 보호성, 사용자 참여도, 포용성(Inclusivity), 사용자 지원성, 자기서술성
- 작성 패턴: "<정의된 사용자군>은 <과업>을 <n>회 이내 시도/<t>분 이내에 완료할 수 있어야 한다."
- 실행 가능한 검증방안: 정해진 태스크 시나리오로 사용성 테스트(대표 사용자 표본), SUS(System Usability Scale) 점수 임계값, 접근성 자동검사 도구(axe 등).
- 지양할 예시: "모든 사용자가 만족해야 한다" → 주관적·전수 조건이라 검증 불가. 대표 표본 크기와 척도(예: SUS 68점 이상)로 재정의해야 한다.

## 4. 신뢰성 (Reliability)
- 하위특성: 무결함성(Faultlessness), 가용성(Availability), 결함허용성(Fault tolerance), 복구성(Recoverability)
- 작성 패턴: "시스템은 <운영 기간> 동안 가용률 <%>를 유지해야 하며, <장애 유형> 발생 시 <시간> 이내 복구되어야 한다."
- 실행 가능한 검증방안: 장애주입 테스트(fault injection), 정해진 기간의 가동률 모니터링 로그 분석, 복구시간 측정 시나리오 테스트.
- 지양할 예시: "절대 고장 나지 않아야 한다" → 무결함을 무한정 요구하는 것은 검증 불가능. MTBF/가용률 등 측정 가능한 목표치로 재정의해야 한다.

## 5. 보안성 (Security)
- 하위특성: 기밀성(Confidentiality), 무결성(Integrity), 부인방지성(Non-repudiation), 책임추적성(Accountability), 인증성(Authenticity), 저항성(Resistance)
- 작성 패턴: "시스템은 <자산/데이터>에 대해 <위협 모델>을 기준으로 <보안통제>를 적용해야 한다."
- 실행 가능한 검증방안: 정적/동적 보안분석(SAST/DAST), 침투테스트(범위 명시), 정해진 CWE/CVE 체크리스트 기반 코드 리뷰.
- 지양할 예시: "모든 해킹을 막아야 한다" → 무한한 위협 범위는 검증 불가. 대상 위협 모델(예: OWASP Top 10, STRIDE 특정 항목)을 한정해야 한다.

## 6. 유지보수성 (Maintainability)
- 하위특성: 모듈성(Modularity), 재사용성(Reusability), 분석용이성(Analyzability), 수정용이성(Modifiability), 시험용이성(Testability)
- 작성 패턴: "<변경 유형>에 대한 평균 수정 소요시간은 <시간> 이내여야 하며, 순환복잡도는 <임계값> 이하로 유지해야 한다."
- 실행 가능한 검증방안: 정적분석 도구(SonarQube 등)의 코드 품질 지표 측정, 리팩토링 소요시간 실측.
- 지양할 예시: "유지보수하기 쉬워야 한다" → 정량 기준이 없어 판정 불가. 코드 품질 지표·임계값으로 재정의해야 한다.

## 7. 유연성 (Flexibility, 구 이식성)
- 하위특성: 적응성(Adaptability), 설치용이성(Installability), 대체용이성(Replaceability), 확장성(Scalability)
- 작성 패턴: "시스템은 <대상 플랫폼/환경> 목록에 <조건>으로 설치·이식 가능해야 하며, 부하 <n>배 증가 시 <자원 증설 방식>으로 대응 가능해야 한다."
- 실행 가능한 검증방안: 지정된 플랫폼 목록에서 설치·구동 테스트, 수평 확장 시나리오의 부하테스트.
- 지양할 예시: "모든 플랫폼에서 동작해야 한다" → 대상 플랫폼을 특정해야 검증 가능.

## 8. 안전성 (Safety) — ISO 26262와 직결
- 하위특성: 운용제약(Operational constraint), 위험식별성(Risk identification), 고장안전성(Fail-safe), 위험경고성(Hazard warning), 안전통합성(Safe integration)
- 작성 패턴: "<식별된 위해(hazard)>에 대해 시스템은 <안전상태(safe state)>로 <시간> 이내 전이해야 한다." (ASIL 등급에 따른 시간/조건 명시)
- 실행 가능한 검증방안: HARA(위해분석 및 리스크평가) 결과와 연계한 안전요구사항 시험, 고장주입 기반 안전상태 전이시간 측정, FMEA/FTA 결과와의 정합성 리뷰.
- 지양할 예시: "위험한 상황이 절대 발생하지 않아야 한다" → 절대적 무위험은 검증 불가능. 식별된 위해 목록별로 안전상태 정의와 전이조건·시간을 명시해야 한다.
- 참고: 안전성 요구사항은 이 스킬만으로 완결되지 않는다. HARA·안전목표(Safety Goal)·안전요구사항 배분은 ISO 26262-3/-4/-6 프로세스와 함께 다뤄야 하며, 이 스킬은 "요구사항 문장의 작성·추적·검증가능성" 관점만 담당한다.

## 공통 검증방안 실행가능성 자가점검 (모든 특성 공통)
검증방안을 확정하기 전에 아래 세 가지를 모두 "예"로 답할 수 있어야 한다:
1. 지금 프로젝트가 보유했거나 확보 가능한 도구/환경/데이터로 실제로 수행할 수 있는가?
2. 유한한 시간·자원 내에 종료되는가? (전수조사·무한반복·주관적 전원동의를 요구하지 않는가?)
3. 결과가 통과/실패를 객관적 수치로 판정 가능한가?

하나라도 "아니오"이면 검증방안을 다시 설계한다(대표 표본, 벤치마크 임계값, 정적분석, 시뮬레이션 등으로 대체).
