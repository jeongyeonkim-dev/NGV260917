# 양방향 추적성 스킴

> 근거: Automotive SPICE PAM 4.1 SYS.1.BP4, SYS.2.BP5/BP6, SWE.1.BP5/BP6 — "일관성을 확보하고 양방향 추적성을 수립한다(Ensure consistency and establish bidirectional traceability)"가 각 레벨의 필수 베이스프랙티스다. SYS.2 Note 7 / SWE.1 Note 11은 "추적 링크가 존재한다는 것 자체가 정보의 일관성을 의미하지는 않는다"고 명시한다 — 즉 링크만 걸어두는 것으로는 부족하고, 연결된 내용이 실제로 부합하는지 확인해야 한다.

## ID 채번 규칙 (일반 규칙 + 이 프로젝트의 확정 규칙)

이 스킬은 두 가지 상황을 구분한다:
1. **고객/입력 문서가 이미 ID를 부여한 경우**: 그 ID를 그대로 쓴다. 새 접두사를 만들지 않는다.
2. **우리가 처음 채번해야 하는 경우**(고객 문서에 ID가 없을 때): 아래 일반 규칙을 쓴다.

| 레벨 | 접두사(일반 규칙) | 대응 A-SPICE 프로세스/산출물 |
|------|----------------------|------------------------------|
| 이해관계자 요구사항 | `STK-####` | SYS.1 (17-00 Requirement) |
| 시스템 요구사항 | `SYS-REQ-####` | SYS.2 (17-00, 17-54) |
| 소프트웨어 요구사항 | `SW-REQ-####` | SWE.1 (17-00, 17-54) |

### 이 프로젝트(전자식 차일드락 제어 SW)의 확정 채번
고객 문서(`OEM_Sample/OEM-SWR-001`)가 이미 이해관계자 수준 ID(`OEM-SR-###`, `OEM-FR-###`, `OEM-NFR-###`)와 인터페이스 ID(`OEM-IF-###`)를 부여했고, 9절 추적성 표에서 하위 소프트웨어 요구사항 ID를 `SWR-001`~`SWR-021`로 이미 예고했다. 따라서:
- **이해관계자 요구사항**: `OEM-SR-###`(ASIL B 입력) / `OEM-FR-###`(QM) / `OEM-NFR-###`(QM 비기능) — 고객 문서 ID 그대로 사용, `STK-####`로 재채번하지 않는다.
- **소프트웨어 요구사항**: `SWR-001`~`SWR-021` — 고객 문서 9절 추적성 표가 지정한 매핑을 그대로 따른다(예: `OEM-SR-001` → `SWR-007`, `SWR-008`). 새 SWR 번호가 필요하면(문서에 없는 세부 분할 등) 21 이후 번호를 이어서 쓰고 그 사유를 기록한다.
- **시스템 요구사항 레벨(`SYS-REQ-####`)**: 이 프로젝트는 SW-only 공급자 입력이라 별도 시스템 레벨을 두지 않는다 — OEM 요구사항이 곧 시스템 레벨 입력을 겸한다. (시스템 레벨이 필요한 다른 프로젝트에서는 위 일반 규칙의 `SYS-REQ-####`를 쓴다.)
- 비기능요구사항 특성 태그(성능효율성 `-PERF` 등, `iso25010-nfr-checklist.md` 참조)는 `SWR-###` 뒤에 붙인다: 예 `SWR-016-PERF`(결정론 요구 OEM-NFR-001과 연결).
- ID는 한 번 부여되면 재사용하지 않는다. 요구사항이 폐기되어도 ID는 "폐기(deprecated)" 상태로 남기고 삭제하지 않는다.

## 링크 방향과 필드

모든 요구사항 항목에는 두 방향의 링크 필드를 둔다(`template.md`의 TPL-SWE1-001 "9. 하향 할당 및 검증 계획", "11. 추적성" 절):

- **상위 추적(부모)**: 이 요구사항이 어떤 상위 요구사항/니즈에서 파생됐는지. 예: `SWR-007`의 부모는 `OEM-SR-001`.
- **하위 추적(자식)**: 이 요구사항이 어떤 하위 산출물(아키텍처 요소, 상세설계, 코드, SWE.4/5/6 시험)에 할당·검증되는지.

두 방향 모두 채워야 "양방향" 추적이 성립한다.

## 추적매트릭스 (WP_Templates `TPL-TRC-001` 형식 — 확정)

프로젝트 내 단일 위치에 전체 추적 관계를 집계한 매트릭스를 둔다(권장 경로: `docs/traceability/trace-matrix.xlsx` 또는 `.md`, `TPL-TRC-001_양방향 요구사항 추적 매트릭스 템플릿.xlsx`의 "Bidirectional Trace" 시트 구조를 그대로 따른다). 각 산출물을 만들거나 고칠 때마다 이 매트릭스도 함께 갱신한다.

**컬럼(고정, 임의로 바꾸지 않음)**: `Upper Req | SW Req | Architecture | Detailed Design | Code | SWE.4 | SWE.5 | SWE.6 | Coverage`

```
| Upper Req  | SW Req  | Architecture | Detailed Design | Code                        | SWE.4      | SWE.5      | SWE.6      | Coverage |
|------------|---------|--------------|------------------|-----------------------------|------------|------------|------------|----------|
| OEM-SR-001 | SWR-007 | Comp-Arbiter | UNIT-Arbiter-001 | src/arbiter.py::onCrash()   | TC-U-011   | TC-I-004   | TC-S-002   | OK       |
| OEM-SR-001 | SWR-008 | 미배정        | 미배정            | 미구현                       | 미배정      | 미배정      | 미배정      | 갭       |
```

- "SWE.4/5/6" 컬럼에는 각 프로세스가 만드는 시험 케이스 ID(`tdd`가 만드는 단위시험, `integration-tester`가 만드는 통합시험, `sw-system-tester`가 만드는 시스템시험)를 적는다.
- "Coverage" 컬럼은 이 행(하나의 SW Req)이 Architecture~SWE.6까지 전 구간에 걸쳐 빠짐없이 연결됐는지(`OK`) 아니면 어디서 끊겼는지(`갭`)를 한눈에 보여준다.

## 점검해야 할 이상 패턴

- **고아 요구사항(Orphan)**: 상위 추적이 없는 `SWR-###`. 왜 존재하는지, 어떤 `OEM-*` 요구에서 파생됐어야 하는지 확인한다.
- **커버리지 갭(Coverage gap)**: Architecture~SWE.6 중 어느 한 칸이라도 "미배정"이면 갭으로 표시한다. 프로젝트 단계상 아직 이르면 정상(해당 Phase가 아직 그 단계에 도달하지 않음)이고, 이미 지나간 단계라면 결함으로 보고한다.
- **중복 추적**: 동일한 하위 산출물이 서로 모순되는 두 상위 요구사항에 동시에 연결된 경우.
- **끊어진 링크**: ID가 매트릭스나 문서 어디에도 존재하지 않는 경우.

## 다이어그램과의 연계
UML/SysML 다이어그램을 사용하는 기능요구사항의 경우, 다이어그램 요소(유스케이스, 블록, 상태 등)에 대응하는 요구사항 ID(`SWR-###`)를 라벨이나 주석으로 표기한다. SysML을 쓸 수 있는 환경이면 `«satisfy»`, `«derive»`, `«verify»` 관계로 요구사항 다이어그램에 직접 추적 관계를 시각화할 수 있다 — 이 경우에도 텍스트/엑셀 기반 추적매트릭스는 별도로 유지한다.
