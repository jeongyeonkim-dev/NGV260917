# 요구사항 특성 체크리스트 (ISO 26262-8 Clause 6 · A-SPICE 4.1 SYS.2/SWE.1 근거)

> 근거: Automotive SPICE PAM 4.1의 **SYS.2.BP1**과 **SWE.1.BP1** 각 Note에는 다음과 같이 명시되어 있다(원문 요지, 영문 병기):
>
> "요구사항의 특성은 ISO IEEE 29148, ISO 26262-8:2018, INCOSE Guide for Writing Requirements 같은 표준에 정의되어 있다. 여러 기술표준이 공유하는 대표적인 특성 예시는 다음과 같다: **검증가능성(verifiability, 검증 기준이 요구사항 문장 자체에 내재)**, **비모호성/이해가능성(unambiguity/comprehensibility)**, **설계·구현으로부터의 자유(freedom from design and implementation)**, **다른 요구사항과 모순되지 않음(not contradicting any other requirement)**." (PAM 4.1 §4.3.2 SYS.2.BP1 Note1–2, §4.4.1 SWE.1.BP1 Note1–2)
>
> 이 스킬은 위 근거를 바탕으로, ISO 26262-8:2018 Clause 6(요구사항 명세)에서 통상 요구하는 특성을 아래 체크리스트로 구체화했다. 인증심사 등 법적 근거가 필요한 경우 조직이 보유한 ISO 26262-8:2018 정본 Clause 6 조항 번호로 재확인한다.

## 요구사항 작성 시 반드시 만족해야 할 특성

| 특성 | 의미 | 점검 방법 |
|------|------|-----------|
| 고유 식별성 (Unique identification) | 모든 요구사항이 변경되지 않는 고유 ID를 가진다 | `traceability-scheme.md`의 채번 규칙 준수 여부 확인 |
| 비모호성 (Unambiguous) | 하나의 해석만 가능하다 | "적절히", "가능한 한", "일반적으로" 등 모호 표현 검색 및 제거 |
| 이해가능성 (Comprehensible) | 해당 분야 이해관계자가 추가 설명 없이 이해 가능하다 | 약어·전문용어 최초 정의 여부, 문장이 3단어 이하 종속절로 구성됐는지 |
| 원자성 (Atomic / Singular) | 하나의 요구사항은 하나의 개념만 다룬다(더 쪼갤 수 없음) | "그리고", "또는", 쉼표로 나열된 복수 조건이 있으면 분리 검토 |
| 완전성 (Complete) | 요구사항 자체로 필요한 조건·제약이 다 서술되어 있다 | 조건/전제/예외가 빠져 있지 않은지 확인 |
| 일관성 (Consistent) | 다른 요구사항과 모순되지 않는다 | 동일 대상(파라미터·인터페이스 등)을 다루는 다른 요구사항과 교차 검토 |
| 실현가능성 (Feasible) | 현재 기술·일정·예산 제약 내에서 구현 가능하다 | 기술타당성 검토(SYS.2.BP3/SWE.1.BP3에 해당) 근거 존재 여부 |
| 검증가능성 (Verifiable) | 검증 기준이 요구사항 문장 자체에 내재되어, 통과/실패를 객관적으로 판정할 수 있다 | 정량적 임계값·조건이 포함되어 있는지, 실행 가능한 검증방안이 짝지어져 있는지 |
| 설계로부터의 자유 (Freedom from design and implementation) | "무엇을(what)"을 규정하고 "어떻게(how)"는 규정하지 않는다(설계는 SYS.3/SWE.2에서 다룸) | 특정 알고리즘·자료구조·구현 기술을 강제하는 표현이 있는지 확인 |
| 추적 가능성 (Traceable) | 상위 근거와 하위 산출물로 양방향 링크가 존재한다 | `traceability-scheme.md` 절차 적용 여부 |

## 실무 작성 규칙
- **능동태·단문**을 사용한다. 수동태는 행위 주체가 불명확해져 이해가능성을 해친다.
- **정량 표현**을 쓴다 — "빠르게" 대신 "200ms 이내", "충분히" 대신 "±0.5% 이내" 등.
- **금지어 목록**(발견 시 재작성): 적절히, 가능한 한, 일반적으로, 필요 시, 충분히, 등등, 최대한.
- **하나의 문장 = 하나의 요구사항**. "시스템은 A를 수행하고 B를 지원해야 한다"는 A/B 두 개로 분리한다.
- **대명사 지양**: "그것", "이것", "해당 기능" 대신 구체적 명사를 반복 사용한다(길어지더라도 명확성이 우선).
- **용어집**: 문서 내에서 처음 등장하는 약어·전문용어는 정의하거나 프로젝트 공통 용어집에 링크한다.
- **설계 배제**: 요구사항에는 "왜/무엇을"만 담고, "어떻게(구현 방법)"는 SYS.3(시스템 아키텍처)/SWE.2(소프트웨어 아키텍처) 영역으로 넘긴다.
