# ISO 26262-6 소프트웨어 통합시험 기법·커버리지 지표 (요약·재구성)

> 근거: ISO 26262-6:2018, 소프트웨어 통합시험(6-10) 관련 절과 구조적 커버리지 표. **아래 내용은 표준 원문의 verbatim 인용이 아니라 업계에 널리 공유된 요지를 한국어로 재구성한 것**이다 — 정확한 조항·표 번호는 판(2011/2018) 사이에 다를 수 있으므로, 인증심사·법적 근거가 필요하면 조직이 보유한 정본과 반드시 대조 확인한다.

## 소프트웨어 통합시험 기법

| 기법 | 요지 | 이 스킬에서의 적용 |
|------|------|----------------------|
| 요구사항기반시험(Requirements-based test) | 소프트웨어 요구사항·인터페이스 명세에서 직접 도출한 시험 | `architecture-designer`의 인터페이스 명세 + `requirements-analyst`의 SW-REQ를 근거로 도출 |
| 인터페이스시험(Interface test) | 컴포넌트 간 인터페이스의 데이터 전달·해석·타이밍이 명세대로 동작하는지 검증 | 이 스킬의 핵심 기법 — 모든 인터페이스에 최소 1개 이상 적용 |
| 결함주입시험(Fault injection test) | 의도적으로 결함(잘못된 입력, 타이밍 위반, 자원 고갈 등)을 주입해 오류처리·안전상태 전이를 검증 | ASIL이 높은 인터페이스·컴포넌트에 우선 적용, `detailed-design`의 오류처리 명세를 근거로 함 |
| 자원사용시험(Resource usage test) | 메모리, CPU, 스택, 통신대역 등 자원소모가 목표치 내에 있는지 검증 | 실시간성이 중요한 통합 단계(특히 `architecture-style-catalog.md`에서 이벤트기반/파이프라인 스타일을 선택한 경우)에 적용 |
| 백투백비교시험(Back-to-back test) | 모델(있는 경우)과 실제 코드의 동작을 동일 입력에 대해 비교 | 모델 기반 설계 산출물이 있는 컴포넌트에 한해 적용(해당 없으면 생략하고 사유 기록) |

ASIL이 높아질수록(C/D) 위 기법들의 권고 수준이 강해진다(권장 → 강력 권장). 어떤 기법을 적용/생략했는지와 그 사유를 시험 계획에 기록한다.

## 시험 케이스 도출 기법 (통합 수준)
단위 수준과 동일한 4가지 기법을 통합 수준(인터페이스 파라미터, 컴포넌트 간 상호작용)에 적용한다 — `tdd` 스킬의 `references/test-case-design.md`를 그대로 재사용한다:
- 요구사항 분석(관련 SW-REQ, 인터페이스 명세로부터)
- 동등분할(인터페이스 파라미터의 정상/특수/오류 카테고리)
- 경계값분석(인터페이스 파라미터의 유효범위 경계)
- 오류추측(설계된 오류처리 동작에 대한 검증)

## 구조적 커버리지 지표 — 함수 커버리지 · Call 커버리지 (이 스킬의 필수 목표)

통합 수준에서는 단위 수준(구문/분기/MC-DC)과 다른 지표를 쓴다:

- **함수 커버리지(Function Coverage)**: 프로그램에 존재하는 함수(서브루틴) 중, 시험 실행 중 적어도 한 번 호출된 함수의 비율.
- **Call 커버리지(Call Coverage)**: 코드에 존재하는 함수 호출 지점(call site) 중, 시험 실행 중 적어도 한 번 실행된 호출 지점의 비율.

**중요한 차이**: 함수 커버리지 100%는 모든 함수가 "어디선가 한 번은" 호출되었다는 뜻일 뿐이다. 같은 함수를 여러 위치에서 호출하는 경우, 그중 한 곳만 실행되어도 함수 커버리지는 100%가 될 수 있다. **Call 커버리지는 모든 개별 호출 지점이 각각 실행되었는지**를 요구하므로 더 엄격하다 — 함수 커버리지 100%가 Call 커버리지 100%를 보장하지 않는다.

ASIL이 높아질수록(C/D) 두 지표 모두 강력 권장된다. 이 스킬은 사용자 요구에 따라 **ASIL과 무관하게 두 지표 모두 100%를 목표**로 삼는다.

## 커버리지 미달 시 처리 원칙
100%에 도달하지 못한 항목은 다음 중 하나로만 종결한다(임의로 무시하지 않는다):
1. **시험 케이스 보강**: 해당 함수/호출 지점을 실행하는 시험을 추가한다(가장 우선).
2. **도달 불가능성 근거 문서화**: 정상적인 시험으로는 도달할 수 없는 방어적 코드(예: 하드웨어 결함이 있어야만 도달하는 안전 처리 경로)임을 결함주입시험 결과나 코드 분석으로 입증하고, 그 근거를 기록해 리뷰받는다.
근거 없이 "테스트하기 어려워서 생략"하는 것은 허용하지 않는다. 상세 절차는 `references/coverage-100-percent-strategy.md` 참조.
