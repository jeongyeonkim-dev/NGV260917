# SOLID 원칙 — 아키텍처 설계 체크리스트

각 원칙을 "컴포넌트/인터페이스 설계에서 무엇을 확인해야 하는가"로 구체화했다. 위반이 발견되면 재설계하거나, 불가피한 경우 사유와 대안(완화조치)을 설계서에 기록한다.

## SRP — 단일 책임 원칙 (Single Responsibility Principle)
- **정의**: 하나의 컴포넌트는 변경되어야 할 이유를 하나만 가져야 한다.
- **점검**: 컴포넌트의 책임을 한 문장으로 요약할 수 있는가? "그리고"로 연결해야 설명되는 컴포넌트는 분할 대상이다.
- **연결**: 높은 응집도(iso26262-6-design-principles.md)와 직결 — SRP를 지키면 응집도가 자연히 높아진다.

## OCP — 개방-폐쇄 원칙 (Open/Closed Principle)
- **정의**: 확장에는 열려 있고, 수정에는 닫혀 있어야 한다.
- **점검**: 새로운 변형(파생 기능, 신규 변형 사양)을 추가할 때 기존 컴포넌트의 내부 구현을 고쳐야 하는가, 아니면 새 구현을 추가하고 인터페이스에 연결하기만 하면 되는가? 후자여야 한다.
- **연결**: "변경에 유연하게 대처"라는 사용자 요구사항의 핵심 원칙. 확장 지점(추상 인터페이스, 플러그인 구조)을 미리 식별한다.

## LSP — 리스코프 치환 원칙 (Liskov Substitution Principle)
- **정의**: 인터페이스의 어떤 구현체로 교체해도 그 인터페이스를 사용하는 쪽의 동작이 깨지지 않아야 한다.
- **점검**: 인터페이스 계약(사전조건/사후조건/타이밍/오류처리)이 명확히 문서화되어 있고, 모든 구현체가 그 계약을 동일하게 지키는가? 특정 구현체만 더 강한 사전조건을 요구하거나 다른 오류처리를 하면 위반이다.
- **연결**: 통합 순서 정의 시 스텁/드라이버로 실제 구현을 대체할 수 있으려면 LSP가 지켜져야 한다.

## ISP — 인터페이스 분리 원칙 (Interface Segregation Principle)
- **정의**: 클라이언트가 사용하지 않는 인터페이스에 의존하도록 강요해서는 안 된다.
- **점검**: 하나의 인터페이스에 서로 관련 없는 오퍼레이션이 섞여 있지 않은가? 특정 클라이언트가 인터페이스의 일부만 쓰면서 나머지 때문에 불필요한 재컴파일·재검증 영향을 받지 않는가?
- **연결**: 인터페이스 명세(interface-first-design.md) 작성 시 "이 인터페이스를 쓰는 컴포넌트가 실제로 이 오퍼레이션을 다 쓰는가?"를 항목별로 점검한다.

## DIP — 의존성 역전 원칙 (Dependency Inversion Principle)
- **정의**: 상위 수준 모듈은 하위 수준 모듈의 구체적 구현이 아니라 추상화(인터페이스)에 의존해야 한다.
- **점검**: 상위 컴포넌트가 하위 컴포넌트의 헤더/구현 세부사항을 직접 include·참조하고 있지 않은가? 상위 컴포넌트는 인터페이스 타입만 알고, 실제 구현체는 조립(assembly/통합) 단계에서 주입되는가?
- **연결**: "컴포넌트 사이에 인터페이스로만 통신"이라는 사용자 요구사항을 구조적으로 강제하는 핵심 원칙.

## 종합 검토 순서
1. 각 컴포넌트에 대해 SRP 위반 여부(책임이 여러 개인지) 확인.
2. 컴포넌트 간 관계에서 OCP 위반 여부(확장 시 기존 코드 수정 필요 여부) 확인.
3. 인터페이스별로 ISP 위반 여부(불필요한 오퍼레이션 강제) 확인.
4. 인터페이스에 다중 구현체가 있거나 예정되어 있다면 LSP 위반 여부(계약 불일치) 확인.
5. 의존 방향을 추적해 DIP 위반 여부(상위가 하위 구현에 직접 의존) 확인 — 이는 낮은 결합도 원칙과도 겹치므로 이미 3~4단계에서 잡힌 결합도 문제와 교차 확인한다.
