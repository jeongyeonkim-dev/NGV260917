# 컴포넌트 통합 순서 정의 절차

> 근거: A-SPICE 4.1 SYS.4.BP1/BP3(시스템 레벨), SWE.5(소프트웨어 레벨)는 공통적으로 "정의된 순서와 사전조건에 따라 통합한다"를 요구하며, 산출물로 **06-50 통합순서 지침(Integration Sequence Instruction)**을 요구한다(`aspice-architecture-bp.md` 참조).

## 절차

### 1. 의존성 그래프 작성
`interface-first-design.md`에서 정의한 제공(provided)/요구(required) 인터페이스를 기준으로, "어떤 컴포넌트가 어떤 컴포넌트의 인터페이스를 필요로 하는가"를 방향 그래프로 그린다(노드=컴포넌트, 화살표=요구 방향).

### 2. 순환 의존 점검
그래프에 순환(cycle)이 있으면 **통합 순서를 정의할 수 없다** — 이는 낮은 결합도 원칙의 근본적 위반이다. 통합 순서를 억지로 정하지 말고, SKILL.md 3~4단계(정적 구조/인터페이스)로 돌아가 순환을 끊는 재설계(예: 공통 상위 컴포넌트로 의존 방향 통일, 이벤트 기반으로 전환, 인터페이스 재설계)를 먼저 수행한다.

### 3. 위상정렬로 통합 순서 초안 도출
순환이 없는 그래프에 대해 위상정렬(topological sort)을 적용해, 의존 대상이 먼저 통합되는 순서 초안을 만든다. 여러 개의 유효한 순서가 나올 수 있으므로, 4번에서 전략에 따라 하나를 선택한다.

### 4. 통합 전략 선택 (근거를 반드시 기록)

| 전략 | 방식 | 적합한 상황 | 트레이드오프 |
|------|------|--------------|----------------|
| 상향식(Bottom-up) | 의존되는 하위 컴포넌트부터 통합 | 하위 컴포넌트가 안정적이고 재사용 비중이 높을 때 | 상위 통합 구조 검증이 늦어짐 |
| 하향식(Top-down) | 상위 구조부터 통합하고 미완성 하위는 스텁으로 대체 | 전체 흐름/사용자 시나리오를 조기에 검증하고 싶을 때 | 스텁 관리 비용, 하위 결함 발견이 늦어짐 |
| 샌드위치(Sandwich/Hybrid) | 상·하위를 동시에 진행해 중간에서 만남 | 상하위 모두 조기 검증이 필요할 때 | 관리 복잡도 증가 |
| 위험기반(Risk-based) | ASIL이 높거나 신규 개발 비중이 큰 컴포넌트를 우선 통합 | 안전 관련 컴포넌트의 리스크를 조기에 노출시키고 싶을 때 | 의존관계상 선행 조건이 안 맞으면 스텁 필요 |

### 5. 단계별 사전조건·검증항목 명시
각 통합 단계마다 다음을 기록한다(SYS.4.BP1/BP3 요구사항 그대로):
- 통합 대상 컴포넌트(들)
- 사전조건(예: 선행 컴포넌트의 단위검증/자격인증 완료 여부)
- 필요한 스텁·드라이버·테스트 하네스
- 이 단계에서 수행할 검증방법과 통과/실패 기준
- 통합 실패 시 회귀(regression) 대상 범위

### 6. 산출물 형식 (06-50 통합순서 지침)

```
| 단계 | 통합 대상 컴포넌트 | 사전조건 | 사용 스텁/드라이버 | 검증 항목 | 비고 |
|------|--------------------|----------|----------------------|-----------|------|
| 1    | Comp-A (최하위)     | 단위검증 완료 | 없음 | 인터페이스 A1 응답 검증 | |
| 2    | Comp-B, Comp-C      | 1단계 완료, Comp-B/C 단위검증 완료 | Comp-D 스텁 | A-B, A-C 인터페이스 시퀀스 검증 | |
| 3    | Comp-D              | 2단계 완료 | 없음 | 전체 시나리오 시퀀스 검증 | 위험기반: ASIL C |
```

### 7. 추적성 연결
이 통합순서는 요구사항 추적성의 "하위 추적" 근거가 된다 — `requirements-analyst` 스킬의 추적매트릭스에 각 통합 단계의 검증항목을 테스트케이스 ID와 연결해 반영할 수 있다.
