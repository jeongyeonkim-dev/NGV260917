# 인터페이스 우선 설계 규칙 (컴포넌트 간 통신은 인터페이스로만)

> 근거: ISO 26262-6 Clause 7 인터페이스 정의 요구사항(`iso26262-6-design-principles.md` 참조), A-SPICE SWE.2.BP1/SYS.3.BP1(정적 측면 명세에 인터페이스 포함), SOLID의 DIP/ISP(`solid-principles.md`).

## 원칙
**컴포넌트 간의 모든 상호작용은 사전에 정의되고 합의된 인터페이스를 통해서만 이루어진다.** 다음은 인터페이스를 우회하는 것으로 간주해 금지한다:

- 전역변수·공유 상태를 통한 암묵적 데이터 교환
- 다른 컴포넌트의 내부 필드·자료구조에 대한 직접 접근
- 구현 세부사항이 노출되는 헤더 직접 include(구현이 아닌 인터페이스 헤더만 참조해야 함)
- friend 클래스, 리플렉션 등으로 캡슐화를 우회하는 접근
- "일단 편하니까" 임시로 만든 백도어성 호출 경로(설계서에 문서화되지 않은 경로)

## 인터페이스 명세 필수 항목
각 인터페이스는 아래 항목을 모두 포함해야 "정의되었다"고 인정한다. 하나라도 빠지면 미완성으로 표시하고 보완한다.

| 항목 | 설명 |
|------|------|
| 이름 | 오퍼레이션/시그널/이벤트의 고유 명칭 |
| 방향 | 제공(provided) / 요구(required) 구분 |
| 데이터 타입 | 파라미터·반환값의 타입 |
| 유효범위 | 값의 최소/최대, 허용 범위 |
| 단위 | 물리 단위(있는 경우) — 예: ms, %, °C |
| 정밀도 | 필요한 경우 소수점/양자화 단위 |
| 타이밍/시퀀스 제약 | 호출 주기, 최대 응답시간, 호출 순서 제약 |
| 오류·예외 처리 | 실패 시 반환코드/예외/타임아웃 동작과 호출자의 대응 |
| 재진입성/스레드 안전성 | 동시 호출 가능 여부, 필요한 동기화 방식 |
| 버전 | 인터페이스 변경 이력 추적을 위한 버전 표기 |

## 설계 절차
1. 컴포넌트 구조(3단계)가 정해지면, 구현에 들어가기 **전에** 컴포넌트 쌍별 인터페이스를 먼저 합의한다(A-SPICE SWE.2.BP5 "합의된 아키텍처 전달"과 연결).
2. 인터페이스는 제공자 관점이 아니라 **사용자(클라이언트) 관점에서 최소한으로** 설계한다(ISP). 클라이언트마다 실제로 쓰는 오퍼레이션만 노출되도록 인터페이스를 분리한다.
3. 상위 컴포넌트는 인터페이스(추상 타입)에만 의존하고, 구체 구현체는 통합·조립 단계에서 연결한다(DIP).
4. 인터페이스가 변경되면, 그 인터페이스를 사용하는 모든 컴포넌트에 대한 영향분석을 수행하고(요구사항 변경관리 SUP.10과 연결), 관련자에게 통지한 뒤 버전을 올린다.
5. 검토 시 "이 두 컴포넌트가 인터페이스 표에 없는 방식으로 상호작용하는 지점이 있는가?"를 반드시 확인한다 — 있으면 결함으로 기록하고 인터페이스를 추가하거나 통신 경로를 제거한다.

## 자가점검 질문 (설계 리뷰 시 사용)
- 이 컴포넌트를 다른 팀이 재구현한다면, 인터페이스 명세만 보고 정확히 같은 동작을 만들 수 있는가? (아니라면 명세가 불완전한 것이다)
- 이 인터페이스를 쓰는 컴포넌트가 실제로 모든 오퍼레이션을 사용하는가? (아니면 ISP 위반 가능성)
- 이 인터페이스의 구현체를 교체해도 호출자가 코드를 고치지 않고 동작하는가? (아니면 LSP/DIP 위반 가능성)
