# 아키텍처 설계 스킬 (A-SPICE · ISO 26262 Part 6 정합)

지정된 설계서 양식에 맞춰, A-SPICE 4.1(SYS.3 시스템 아키텍처 설계, SWE.2 소프트웨어 아키텍처 설계, SYS.4/SWE.5 통합 및 통합검증)과 ISO 26262 Part 6 Clause 7(소프트웨어 아키텍처 설계)을 만족하는 아키텍처를 설계한다. 이 스킬의 목표는 다음 품질 게이트를 모두 통과하는 아키텍처를 만드는 것이다.

1. **설계서 양식 준수** — 사용자가 지정한 아키텍처 설계서 양식을 그대로 따른다.
2. **표준 준수** — A-SPICE SYS.3/SWE.2 베이스프랙티스와 ISO 26262-6 Clause 7 설계원칙을 충족한다.
3. **높은 응집력·낮은 결합도(필수)** — 타협 불가 원칙. 위반이 발견되면 반드시 재설계한다.
4. **변경 유연성** — 예상 가능한 변경에 국소적으로만 대응하도록 설계한다.
5. **SOLID 원칙 준수**.
6. **인터페이스 정의 및 인터페이스 전용 통신(필수)** — 모든 컴포넌트 간 상호작용은 명시적으로 정의된 인터페이스를 통해서만 이루어진다.
7. **컴포넌트 통합 순서 정의** — 의존성에 근거한 통합 순서와 각 단계의 사전조건·검증항목을 명시한다.
8. **후보 제안 후 사용자 선정** — 상세설계 전에 반드시 후보 아키텍처를 제시하고 사용자의 선택을 받는다(자동 진행 금지).

정확한 근거 표준 원문과 체크리스트는 `references/`에 있으며, 단계별로 필요한 파일을 읽어서 적용한다.

## 0단계 — 설계서 양식 확인 (선행 조건)

`references/template.md`를 먼저 읽는다.

- **"임시(INTERIM) 템플릿"**으로 표시되어 있으면 사용자가 실제 설계서 양식을 아직 제공하지 않은 상태다. 임시 양식으로 초안을 작성할 수는 있으나, 결과물 상단에 "⚠ 사용자 지정 설계서 양식 미수령 — 임시 양식 기준으로 작성됨"을 반드시 명시한다.
- 사용자가 실제 양식을 제공하면 `references/template.md`를 그 내용으로 갱신하고 "임시" 표시를 제거한다.
- `requirements-analyst` 스킬이 이미 프로젝트에 설치되어 있고 요구사항 산출물(SYS-REQ-####, SW-REQ-#### 등)이 존재하면, 그 ID 체계를 그대로 이어받아 아키텍처 요소와의 추적 관계(만족/할당)를 표기한다.

## 절차

### 1단계 — 입력 확인
- 대상 레벨 결정: 시스템 아키텍처(SYS.3) / 소프트웨어 아키텍처(SWE.2).
- 근거가 될 요구사항 목록과 ASIL(있다면), 제약조건(플랫폼, 실시간성 요건, 메모리/연산 자원 한계, 재사용 대상 컴포넌트 유무)을 확인한다. 불명확하면 가정하지 말고 사용자에게 확인한다.

### 2단계 — 후보 아키텍처 제안 및 사용자 선정 (필수 체크포인트 — 여기서 멈춘다)
`references/architecture-style-catalog.md`에서 프로젝트 제약에 맞는 후보를 **최소 2개, 권장 3개** 골라 제시한다. 각 후보에 대해 응집도/결합도 특성, 변경 유연성, 실시간성·결정성, 자동차/임베디드 도메인 적합성, 트레이드오프를 표로 정리한다.

**이 단계에서 절대로 임의로 하나를 확정해 다음 단계로 진행하지 않는다.** `AskUserQuestion` 도구를 쓸 수 있으면 그것으로 선택을 받고, 쓸 수 없는 실행 맥락이면 응답을 후보 비교표로 마무리하고 사용자의 다음 메시지(선택)를 기다린다. 사용자가 후보 외의 절충안이나 커스텀 구조를 원하면 그것을 반영해 재제안한다.

### 3단계 — 정적 구조 설계
선택된 스타일을 기준으로 컴포넌트 계층 구조를 설계한다(ISO 26262-6 Clause 7의 계층적 구조 원칙, `references/iso26262-6-design-principles.md` 참조).
- 각 컴포넌트에 단일 책임을 부여한다(SOLID의 SRP, `references/solid-principles.md`).
- 컴포넌트 크기·복잡도를 제한한다 — 하나의 컴포넌트가 과도하게 커지면(God Component) 분할한다.
- **응집도·결합도 자가점검(필수, 위반 시 재설계)**: 컴포넌트 내부 요소들이 하나의 책임을 위해 강하게 협력하는가(고응집)? 컴포넌트 간 의존이 인터페이스 개수·데이터 개수 기준으로 최소화되어 있는가(저결합)? 순환 의존성이 있는가(있으면 즉시 결함으로 표시하고 제거)?

### 4단계 — 인터페이스 정의 (필수 체크포인트)
`references/interface-first-design.md`의 규칙에 따라 **모든** 컴포넌트 쌍 간 상호작용에 대해 인터페이스를 명세한다.
- 전역변수 공유, 컴포넌트 내부 필드 직접 접근, 구현 세부사항 노출을 통한 암묵적 통신을 금지한다.
- 인터페이스 명세에는 오퍼레이션/시그널명, 방향(제공/요구), 데이터 타입·유효범위·단위, 타이밍/시퀀스 제약, 오류·예외 처리 방식을 포함한다.
- 설계 검토 시 "이 컴포넌트가 인터페이스를 거치지 않고 다른 컴포넌트에 접근하는 경로가 있는가?"를 명시적으로 점검하고, 있으면 결함으로 기록한다.

### 5단계 — 동적 측면 설계
컴포넌트 간 상호작용 순서, 모드/상태 전이, 타이밍 제약을 설계한다(ISO 26262-6 Clause 7의 정적/동적 측면 구분, A-SPICE SYS.3.BP2/SWE.2.BP2 대응). 필요하면 `requirements-analyst` 스킬의 `references/uml-sysml-notation.md`(시퀀스/상태기계/블록정의 다이어그램)를 재사용한다.

### 6단계 — SOLID 및 설계원칙 재검토
`references/solid-principles.md`의 체크리스트로 설계 전체를 재검토한다: SRP 위반(다중 책임), OCP 위반(확장 시마다 기존 코드 수정 필요), LSP 위반(대체 불가능한 하위구현), ISP 위반(비대한 인터페이스), DIP 위반(상위 컴포넌트가 구체 구현에 직접 의존). 발견된 위반은 재설계하거나, 불가피하면 사유와 대안(완화조치)을 기록한다.

### 7단계 — 컴포넌트 통합 순서 정의
`references/integration-sequence.md`의 절차대로 진행한다:
1. 컴포넌트 의존성 그래프 작성(제공/요구 인터페이스 기준).
2. 위상정렬로 통합 순서 초안 도출 — 순환이 나오면 3단계로 돌아가 결합도 문제부터 해결한다.
3. 통합 전략(상향식/하향식/샌드위치/위험기반) 중 프로젝트에 맞는 것을 선택하고 근거를 남긴다.
4. 각 통합 단계의 사전조건, 필요한 스텁/드라이버, 해당 단계 검증항목을 명시한다(A-SPICE SYS.4.BP1/BP3 대응, 산출물 06-50 Integration Sequence Instruction).

### 8단계 — 분석·일관성·추적성·커뮤니케이션
- 아키텍처를 기술적 설계 측면(제조성, 재사용 가능성, 성능 등)에서 분석하고 특수특성(Special Characteristics)을 도출한다(SYS.3.BP3).
- 요구사항(SYS-REQ/SW-REQ)과 아키텍처 요소 간 양방향 추적을 수립한다 — `requirements-analyst` 스킬의 `references/traceability-scheme.md`와 동일한 방식(상위: 요구사항 ID, 하위: 아키텍처 요소/컴포넌트 ID)을 사용하고, 가능하면 동일한 추적매트릭스에 통합한다.
- 추적 링크의 존재만으로 충분하지 않다 — 링크된 요구사항과 아키텍처 요소의 내용이 실제로 부합하는지 확인한다(SYS.3 Note 7).
- 합의된 아키텍처와 특수특성을 이해관계자에게 전달할 수 있는 형태로 정리한다(SYS.3.BP5/SWE.2.BP5).

### 9단계 — 산출물 작성
0단계에서 확인한 설계서 양식에 맞춰 최종 문서를 작성한다. 양식이 없으면(임시 상태) 아래 최소 구성을 쓴다:

## 주의사항
- 응집도·결합도, 인터페이스 전용 통신, 후보 제안 후 사용자 선정은 **"반드시"** 지켜야 하는 항목이다 — 시간이 촉박하거나 범위가 작아 보여도 생략하지 않는다.
- 후보 제안 단계를 건너뛰고 하나의 아키텍처로 바로 상세설계에 들어가지 않는다.
- 인터페이스 없이 이루어지는 컴포넌트 간 통신(전역변수, 직접 필드 접근 등)은 발견 즉시 결함으로 기록하고 인터페이스화한다.
- 순환 의존성은 통합 순서를 정의할 수 없게 만드는 근본 결함이다 — 발견되면 통합순서 정의보다 구조 재설계를 먼저 한다.
